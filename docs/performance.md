# Performance

This page explains how the site stays fast: where results are cached, how the cache is kept warm, which database settings matter, and which query patterns we use and avoid. Read it before you write a new RPC query or change the cache.

## How a page is served

Cloudflare sits in front of the origin and caches what the origin marks as shareable (see [The edge cache](#the-edge-cache)). Static assets under `/_app/immutable/` have content-hashed names and are sent with `cache-control: public, max-age=31536000, immutable`, so browsers and the edge keep them for a year. Pages and twins are rendered by the SvelteKit server, which answers each page from a handful of RPC procedures called in-process. A loader starts independent procedure calls together with `Promise.all`, so a contest page waits for its slowest call, not for the sum of them.

Each kind of archive page (contest, election, day, and polity) is its own JavaScript chunk, loaded with a dynamic `import()`, so a contest page doesn't download the code for the other three. That cut the JavaScript a contest page preloads from about 473 kB to 240 kB gzipped.

Two sections of the contest page, the ballot list and the lean chart, sit below the results and can take seconds on a cold cache. They don't hold up the page. The loader starts them once the contest is found. When the main data is ready, it returns each one as a plain value if it has already finished, and as a promise if it hasn't. SvelteKit streams a promise to the browser when it resolves, and the page renders it with `{#await}`. A warm page therefore arrives fully rendered, and a cold one shows the results first and fills in the rest. The Markdown and JSON twins wait for both.

## The edge cache

Cloudflare caches every response that the origin marks as shareable. `mark()` in `apps/web/src/lib/server/edge.ts` determines this as each response leaves the server. A response is shareable when it answers a GET or HEAD with a 200, sets no `cache-control` or `set-cookie` of its own, goes to a visitor who is not signed in and sent no `authorization` or `x-api-key` header, and is not under `/api/auth`, `/mcp`, or `/rpc`. A shareable response gets two headers:

- `cache-control: no-cache`, so browsers keep the page but ask the edge before reusing it. The edge answers with a 304 when the page hasn't changed.
- `cloudflare-cdn-cache-control: public, max-age=300, stale-while-revalidate=604800, stale-if-error=604800`, which only Cloudflare reads and never passes on. The edge serves its copy as fresh for five minutes. For the next seven days it keeps serving that copy at once while it fetches a new one in the background, so a visitor waits for the origin only when the edge has no copy less than a week old. If the origin fails, the edge serves its copy for up to seven days.

Every other response gets `private, no-cache` unless it already set its own `cache-control`, so the edge never stores it.

Page data is shared the same way, with one more check. When someone moves between pages, or between the rounds of a count, the browser fetches the new page's data as `__data.json`. SvelteKit marks every data response `private, no-store`, and it reports a load error inside a 200 instead of with an error status. So `mark()` reads the body of each data response and shares it only when it is plain JSON that starts as page data and holds no error node. A streamed response, a redirect, or a load error keeps SvelteKit's `private, no-store`. A shared data response also gets an ETag, a hash of its body, so a browser that goes back to a round it has already seen gets a 304 from the edge instead of the whole response. On the 2025 New York City Democratic primary for mayor, by election district, a round's data used to come from the origin every time: about 0.3 seconds when the origin was idle, and 1.3 to 1.9 seconds while the warm-up was running. From the edge it takes about 0.15 seconds, and a click on a round paints in 0.3 to 0.47 seconds. The edge compresses a cached copy less tightly than a response that it passes through: browsers that accept zstd get about 371 KB either way, while browsers that accept only brotli get about 360 KB instead of 263 KB.

Live results get a much shorter edge lifetime: `public, max-age=5, stale-while-revalidate=10, stale-if-error=3600`. This covers live pages, their twins, their page data, the live API, and `live.stamp`, the update check that an open live page sends every 30 seconds as a GET. A visitor sees a count at most about 15 seconds older than the origin's, and however many people are watching, the origin answers each of these URLs only once every few seconds per Cloudflare data center. If the origin goes down, the edge keeps serving the last count for up to an hour. Live page data skips the error check that other page data goes through, since a cached error lasts only a few seconds. Live responses that aren't shareable send `no-store`.

The edge keeps one copy of each URL per format and per locale. A page and its Markdown and JSON twins share a URL and differ only by the `Accept` header, so a cache rule sorts each request into `text/html`, `text/markdown`, or `application/json`. The locale never comes from the URL. Before the cache lookup, transform rules set an `x-locale` request header: to the `PARAGLIDE_LOCALE` cookie when the visitor has one, and otherwise to the site locale that matches the first language in `Accept-Language`, if any. Shareable responses send `vary: accept, x-locale`. The origin renders the cookie's locale, or the header's when there is no cookie, and the client reads the rendered locale from the page's `lang` attribute, then saves it in the cookie. A response is shareable only when `x-locale` names a known locale and matches the cookie, if there is one, so a forged header or an unknown locale can't put a page into another locale's copy. Because only the first language counts, each locale has a single cached copy instead of one per `Accept-Language` string.

Requests that carry a session cookie, an `authorization` header, or an `x-api-key` header skip the edge cache entirely: a cache rule matches them before the lookup. The origin also marks those responses private, in case a rule is ever wrong.

Deploys and data copies never purge the whole edge cache. Each shareable response carries a `cache-tag` header holding its page path without the format extension, so `/us`, `/us.md`, `/us.json`, and the page data behind `/us` all share the tag `/us`. When a publish reaches production, the warm-up described below marks those tags stale through Cloudflare's invalidation API: the edge keeps serving its copy and fetches a fresh one in the background. Shipping changed map tiles or page scans purges only those files' URLs. The production purge script sends these requests, and with no arguments it still purges the whole host for emergencies. It needs `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_PURGE_TOKEN`, an API token that can only purge the cache of that zone. Other pages reach visitors within about five minutes, as edge copies expire.

A new build can meet pages that the edge cached from the build before it. Old HTML names script files that the new build doesn't have, and SvelteKit answers 404 for any missing `/_app/` file before the app's hooks run. So each deploy copies the outgoing build's `/_app/immutable/` files to `data/immutable`, and Caddy serves a file from there when it exists, before passing the request to the app. Files leave that folder two weeks after their build stops serving. Page data can't cross builds safely either, because node indices change. So the browser adds its build to every `__data.json` request as `?build=`. This also gives each build its own edge copy. When the build doesn't match the server's, `skewed()` in `edge.ts` answers with a 409 that carries the server's version, and SvelteKit reloads the page in full.

Cloudflare's tiered cache is on, with smart topology. A data center that misses sends the request to an upper-tier data center before the origin, and the upper tier keeps warm connections to the origin. A miss in the eastern United States for France's polity page took about 450 ms past the TLS handshake when every data center went to the origin on its own; through the upper tier it takes about 180 ms, and a hit takes about 50 ms. Every `Accept-Encoding` value shares one edge copy, because the edge compresses each response itself, so one request primes a page for every browser.

Cloudflare keeps the origin's ETag only when no zone feature rewrites the HTML, so Email Obfuscation, Automatic HTTPS Rewrites, Replace insecure JavaScript libraries, Rocket Loader, and injected bot-detection scripts stay off. When Cloudflare compresses a page itself, it turns the ETag into a weak one, which still gets a 304 when the browser checks.

## The procedure cache

Every read procedure goes through `remember()` in `apps/web/src/lib/server/cache.ts`. A result is keyed by the procedure's name and its JSON input, and it lives in three tiers:

- **In-process.** A `Map` used as an LRU, capped at 20,000 entries or 1 GiB of serialized size, whichever comes first.
- **Shared.** Redis, keyed by `c:<code version>:<procedure>:<input>`. Values are serialized with `node:v8`, compressed with zstd, and kept for 30 days. Values larger than 64 MiB are not stored.
- **Persistent.** A separate Postgres database, named by `PAGES_DATABASE_URL`, keeps the same compressed payload under the same key in one table, `entry`. It never evicts, so a result computed once survives Redis evictions, server restarts, and the nightly restore of the archive database, which replaces only that database. A Redis miss reads this table and puts the value back into Redis. The server creates the table on first use and skips this tier when `PAGES_DATABASE_URL` is unset.

When a result is in none of the three tiers, `remember()` takes a lock in Redis before it computes, under `lock:` plus the entry's key, with a 75-second expiry. Another web process that misses on the same key at the same moment waits instead of computing: it checks the shared and persistent tiers every half second and returns the value as soon as the first process stores it. If the lock disappears and no value shows up within about two seconds, or if the wait passes 70 seconds, the waiter computes the result itself. Without the lock, each of the four web processes ran its own copy of a slow query on a cold key, so loading a heavy page, such as the winners for a Turkish local election, sent four copies of the same query to the database at once. The lock covers only the first computation of a key. Background renewals after a publish do not take it, because they already run at most four at a time.

The code version is a fingerprint of the server code that can change a cached result. The `codeVersion()` Vite plugin in `apps/web/code-version.ts` computes it during the server build. It starts from the modules that import `cache.ts` and the modules that import those, follows every static and dynamic import from there, and hashes each module's transformed code. It also hashes `pnpm-lock.yaml` and every file in `packages/db/migrations`, so a dependency upgrade or a schema change counts as new code. The plugin writes the list it hashed to `build/server/code-version.txt`, one line per module. Diffing that file between two builds shows why their versions differ. A deploy that changes only components, styles, or client code keeps the version, so it reads every result the previous build wrote. A deploy that changes a query, a procedure, a dependency, or a migration starts with an empty shared cache, as every deploy did before. In the dev server the plugin returns no version, and the key falls back to the SvelteKit build id.

Two builds of the same commit produce the same version. A rebuild with an edit to a Svelte component kept the version, and an edit to `seats.ts` changed it. Between October 25 and November 1, about one web commit in five touched no server code, so roughly that share of deploys now starts warm. The first deploy of this change to staging was followed by one that changed only a page loader and a component; it kept the version and its 89,000 shared entries, and the new process answered `/us` in 0.2 seconds. Environment variables are not part of the version. If a change to `web.env` changes what a procedure returns, flush the shared cache after the deploy.

Each entry carries the data version that was current when it was computed. The version joins today's date, the number of published and rejected changesets, the time of the latest publish, and the time of the latest coverage build. The server reads it at most every five seconds. When the version moves, a stale entry is still served right away and a background renewal recomputes it. At most four renewals run at once, so the database never gets a burst of heavy queries after a publish. Procedures built with `strict` instead of `os` never serve a stale value: they recompute before answering.

Entries are keyed by locale as well, because names in a result are translated. A `remember()` call that returns only ids and numbers can pass `isNeutral`, its fifth argument, so every locale shares one entry and skips name localization. `universe()` in `archive.ts` uses it for the list of precincts behind a contest's boundaries: the Los Angeles County Superior Court Office 48 boundaries took 161 seconds cold in English, and then 20.6 seconds in German instead of recomputing the 2- to 4-minute recursive query.

## Warming

When a deploy changes server code, it empties the shared cache, and the first visitor to each page would pay for every query. After each such deploy and each database restore, a warm-up script asks the database for the pages people are most likely to open: the home page, every country, supranational body, and federal unit, their recent general elections, and every contest in each one's latest general election. That is about 18,000 pages. The script requests each page three at a time from the origin, which fills both cache tiers in about 35 minutes. Because a country's page loads its latest general election on the server (see "Load a country's map with the page" below), visiting a country also warms the election and hex layout behind its map. The script then requests the same pages through the public hostname, which puts each one in Cloudflare's upper tier, so a visitor anywhere gets a page that is already at the edge.

When the nightly copy of the database reaches production, the restore script notes the newest publish time in the old copy and passes it to the warm-up. Before its usual pass, the warm-up finds what was published since then: the contests, elections (with their parent elections), polities, people, and parties that those changesets wrote, capped at about 900 pages. Live pages are left to the usual pass, which requests them first, and they only stay at the edge for five seconds. The warm-up requests each touched page and its Markdown and JSON versions from the origin two at a time, or one at a time while the live poller runs, with an `x-ea-refresh` header. That header makes `remember()` recompute stale results before answering instead of in the background. Only requests from the loopback address can use it, and Caddy strips it from public requests. The warm-up then marks the same pages stale at the edge by tag. If a later restore interrupts it, `/srv/ea/touched-since` keeps the earlier start time, so the next run covers both publishes.

Deploys are blue-green, so no visitor waits on a process that has just started. The new build starts beside the running one on its own port and takes no traffic until it is warm. If its code version matches the running build's, the shared cache already holds its results, and it only loads each country and federal unit page once to fill its in-process cache. If the version changed, it first renders every country, federal unit, and recent general election, along with every contest that covers a whole country or federal unit, such as a presidential race, a referendum question, or a national list. That comes to about 505 pages, and the old build keeps serving while they render. Caddy then switches to the new build with a graceful reload, which lets requests already in flight finish on the old one. After the switch, the deploy keeps the old build's assets, stops the old build a minute later, and runs the full warm-up. It doesn't purge the edge: cached pages refresh within five minutes, and the build check above keeps old and new page data apart. On staging, a probe requested the home page every 0.2 seconds during a 12-minute deploy and got 2,933 responses, all of them 200.

A polity's record of elections, seats, and winners (`polities.record`) is the slowest payload a polity page asks for, so it is precomputed for every polity with at least 500 contests for its own offices and councils. `ea records` writes each record to the `polity_record` table. The procedure reads the stored row until the next publish and computes the record live after that. The batched rebuild runs `ea records` after each round of publishes. The nightly copy to production runs it just before the database dump, and dumps again if a changeset was published in between, so production reads stored records all day. On November 1, the US record took 5.6 seconds to compute live, 14 seconds on a cold database, and 21 milliseconds from the stored row. The scripts behind `ea records`, `ea parties`, and `ea mosaics` load the app's server code through Vite. When they finish, they unref the Redis client, because its open connection would otherwise keep Node running forever.

A contest counted in rounds, such as a ranked-choice or single transferable vote count, has one page per round, and only `contests.get` reads the round. When someone opens one round, the server computes the contest's other rounds in the background after it answers, one after another: the next round, the previous round, and the final round first, then the rest from nearest to farthest, up to 12 rounds in all. No more than two pages warm their rounds at once, so a burst of visitors cannot pile heavy queries onto the database. In the browser, the round links in the count table preload on hover instead of on tap. On the 2021 New York City Democratic primary for mayor, by election district, the first round took 6.5 seconds cold, and 30 seconds later every other round took 0.4 to 0.55 seconds.

Inside `contests.get`, the queries that don't depend on the round are shared across a contest's rounds: the result sets picked for each place, the covering contests, the channel pools, and the name of the finer level. Each one is cached under a key built from its own inputs, with `across()` in `archive.ts`. These entries are strict, so a page recomputed after a publish never reads one of them stale. Only contests counted in rounds use them, which keeps the in-process cache from filling with entries no other page would read. A cold round of the 2021 primary went from 4.7 seconds to 3.4 seconds, and its database time from 3.7 seconds to 1.9 seconds.

The round's own results are split the same way. For a round, `load()` reads only that round's rows, and the database drops the other rounds inside the index scan instead of reading them. What depends on every round comes from a frame that `stepped()` caches for each set of picked result sets and areas: each area's main measure, the result sets and areas that report it, and the totals that order the options. The options that have no votes in a round are found once per result set for all of its rounds, instead of once for each of the ten or so loads that a single round makes. The label points for the map are cached by their areas and date. A cold round of the 2021 primary now takes 1.2 seconds, 0.4 seconds of it in the database. A cold round of the 2025 primary by election district went from 1.3 to 1.7 seconds, down to 0.75 to 0.97 seconds. Most of what remains is building and sending the response, which is 1.6 MB, or 136 KB compressed.

## Database settings

- **JIT is off.** Our queries are large and generated, and their plans are expensive to compile. With JIT on, one contest page spent 14 of its 34 seconds compiling.
- `random_page_cost = 1.1` and `effective_io_concurrency = 200`, which suit SSD storage.
- After a restore, `vacuumdb --freeze --analyze` runs with eight jobs. Freezing sets the visibility map, so index-only scans skip the heap, and analyzing gives the planner fresh statistics.
- The web app keeps two pools. Pages and the API share one of up to 16 connections, and in production a statement on it stops after 60 seconds, so a page that is slow to render cold fails instead of holding a connection for minutes. A separate pool of up to 8 connections serves live results (`/live`, its shapes and ballots, and the live RPCs, including the stamp every open live page polls), so they never wait behind archive pages. Both pools wait up to 30 seconds for a connection. Scripts that load the server code through Vite keep the 5-minute statement timeout.
- `pg_stat_statements` and `track_io_timing` are on. Rank `pg_stat_statements` by `total_exec_time` to find the next query to fix.

## Query patterns

These patterns came out of plans that read whole tables. Each one turned a query that took seconds into one that takes milliseconds.

- **Start from a small set of ids.** When a query needs rows for a few contests, select the ids first, then fetch rows with `cross join lateral (select ... where rs.contest_id = ids.id offset 0)`. The `offset 0` keeps the planner from flattening the subquery into a hash join over the whole table.
- **Don't join recursive CTE output back to big tables.** Postgres estimates recursive CTEs poorly, so a join from `grp` or `tree` back to `contest` or `election` often becomes a hash join over all of `contest` (about 950,000 rows) or `election` (about 220,000 rows). Fetch the extra columns with a scalar subquery or a lateral instead.
- **Use `= any(array[x])` when an equality would pick the wrong index.** When a column is indexed by a btree and also appears, not first, in a GiST key, a plain equality can lead the planner to the GiST index. `= any(array[x])` steers it to the btree.
- **Don't wrap indexed columns in `coalesce`.** Write `(c.body_id = x or (c.body_id is null and c.office_id = x))`, not `coalesce(c.body_id, c.office_id) = x`, so each branch can use its index.
- **Filter before joining territories.** Find the elections you need first, then join `polity_territory` for only those.
- **Test existence in a select list with `(select true ... limit 1)`.** The planner can turn an `exists` in a select list into a hashed subplan that reads every matching row in the table. A scalar subquery with `limit 1` always runs per row and stops at the first match.
- **Probe geometry through its spatial index first.** Select candidate shapes with `g.geom && ST_MakeEnvelope(...)` in a subquery that ends in `offset 0`, then join `area` and filter by date. Without the optimization fence, the planner can combine the spatial index with the date index in a bitmap AND that reads hundreds of thousands of rows.
- **Fix the leading column of a GiST key.** The keys of `area_geometry`, `area_parent`, and `reporting_unit_area` are GiST indexes on an id and a `valid` range. A probe that fixes only the date scans the whole index. Start from the ids you already have, and look up each one with a lateral subquery.
- **Compute constant sets once.** Put a filter that doesn't depend on the row, such as the list of ICPSR sources or the dates of elections that have polity-wide results, in `= any(array(select ...))` or a materialized CTE. Then it runs once per query instead of once per row.
- **Summarize a CTE once, not once per row.** A scalar subquery such as `(select id from ahead a where a.root = i.id order by a.depth desc limit 1)` reads the whole CTE for every row. Compute `distinct on (root)` once and join the result.
- **Group before you test.** When thousands of rows collapse to a few hundred keys, as when every past contest of a body maps to its districts, group by the key first and run the existence checks on the grouped rows.
- **Fetch notes by entity id.** Put the union of ids first, then fetch matching rows with a lateral lookup by `entity_id`, instead of testing `exists` against the union for every note.
- **Run cheap geometry tests before expensive ones.** Compare bounding boxes with `&&`, or check `ST_Intersects`, before computing `ST_Intersection`. Fold "has no shape" and "overlaps" into one lookup per row instead of two. Clip a heavy shape to the other shape's bounding box with `ST_ClipByBox2D`, wrapped in `ST_MakeValid`, before intersecting them.
- **Make `is not distinct from` joins indexable.** A join on `c.body_id is not distinct from me.body_id` can't use an index. When one side is known to be non-null, add `(c.body_id = me.body_id or c.office_id = me.office_id)` so the planner can probe both indexes, and keep the null-safe test as a filter. For a small constant set, use `= any(array[...])`. The query behind a person's page finds when each of their terms ended by looking for the next election to the same seat, matched with `is not distinct from` on body, office, and district. Each lookup read all of `contest` and joined it to every later election. With the guard added, the lookup for Donald Trump's record went from 2.5 seconds to 0.43 seconds and Eric Adams's from 2.0 seconds to 0.36 seconds, with byte-for-byte the same output for 11 people.
- **Memoize shared helpers.** A contest page runs several procedures, and each one resolves the URL path through `children()`. `children()` and the lean atlases also go through `remember()`, so a page load resolves each path once, and concurrent calls share one query.
- **Rule out candidates before resolving them.** The ballot list checks every contest held in the same place on the same day. A cheap check drops the contests that can't list this place before the expensive path resolution runs: it checks whether the two shapes' bounding boxes overlap, whether the place sits under the contest's area, and whether reporting units link them. On a Cleveland precinct page, the test dropped 112 of 133 candidates, and the ballot went from 20 s to 5 s cold.
- **Split an `or` across different tables into a `union all`.** A filter such as `ct.entity_id = x or ct.entity_id in (select ...)` can't use one index for both branches, so the planner reads every citation. Select each branch on its own and combine them with `union all`; each branch then uses its own index.
- **Compute once per election day, then read per contest.** Many contests share a day, a kind of election, and the areas they report in. Turnout by place is computed for every area of a day and kind, cached under that day and kind, and then filtered to the areas one contest needs. In the same way, a contest map walks a state's areas once per level and day, and reads inset parts once per boundary scheme and day. The first contest of a day pays for the query, and every other contest that day reads the cached result.
- **Start from the smaller side, and decide which side in TypeScript.** Before a contest page looks up the areas below its top areas, a quick count compares the top areas' children with the areas that have results. If the top areas have no children, the lookup is skipped. If fewer areas have results than there are children, the query starts from the areas with results. Make this choice in TypeScript with two queries, not in SQL with a `union` of both directions: `result_value` has 35 partitions, and planning both branches costs more than the branch saves.
- **Look up related rows by their own index.** To find each contest's runoffs, don't group every runoff in the database in a CTE and join it back. Use a lateral subquery per contest, `where n.previous_round_id = c.id`, which reads only that contest's runoffs. Fetch a contest's election the same way, with `cross join lateral (select ... from election x where x.id = c.election_id offset 0)`. On the race list of an election page, this took the query from 107 ms to 3 ms. Resolve merged parties the same way, with a lateral lookup into `entity_merge` by id.
- **Start a slow query as soon as its inputs are known.** Inside `contests.get`, the query for the contests that cover the same place takes 300 to 500 ms cold, and it needs only the contest, its area, its path, and its number of rounds. It used to wait behind about a dozen smaller queries that don't feed it. It now starts as soon as those inputs are known and runs alongside them, and the two small queries that follow it run at the same time as it does. Attach `.catch(() => null)` to a promise you start early, the way `county`, `overall`, and `covers` do. Then an error thrown before the `await` doesn't crash the process as an unhandled rejection, and the later `await` still sees the error.
- **Look up outcomes with a fenced lateral after a recursive CTE.** The query that finds a chamber's composition before an election walks the election's contest tree with a recursive CTE, then joins each contest's options to their declared outcomes. For the 2024 US general election, Postgres estimated 19,616 rows in the tree where there are 435, and with that estimate it chose a merge join that read all 1.15 million rows of `outcome` in index order. A `cross join lateral (select ... from outcome x where x.option_id = o.id ... offset 0)` looks up each option's outcomes through the index instead. The query went from 2.49 seconds to 0.79 seconds and returned the same rows, and a cold `elections.get` for that election went from about 4.9 seconds to 3.2 to 3.6 seconds. Two builds, with and without the change, returned byte-identical `elections.get` results for 74 elections, and the same pages and twins for `/us`, the 2024 general election, its presidential contest, and a Los Angeles County contest.
- **Test a whole shape once, outside the per-part loop.** To find a map's bounds, `framing` dumps each shape into its parts and keeps the parts that are large enough to see. It tested whether each shape was empty in the same select list as the dump, so Postgres ran `ST_IsEmpty` once per part, and each call read the whole shape out of TOAST again. Nunavut has 17,611 parts and 1.2 million points, so that one riding cost 45 million buffer reads. Materializing the CTE did not help, because the materialized rows still hold TOAST pointers. A `cross join lateral (select ST_IsEmpty(w.geom) as empty offset 0)` ahead of the dump runs the test once per shape. The framing query for Canada's 2025 general election went from 161 seconds to 2.6 seconds and returned the same bounds, and a cold `elections.get` for that election went from 146 to 166 seconds down to about 4 seconds. Louisiana's 1900 election went from 56 seconds to 4 seconds. Two builds, with and without the change, returned byte-identical `elections.get` results for 74 elections, in both orders, and the whole set took 123 seconds instead of 384. The same query also inlined its last CTE, `framed`, into both the filter `box is not null` and the select list, so Postgres projected every kept part twice. With `framed as materialized`, the framing query for the 2024 UK general election went from 1.05 seconds to 0.70 seconds and returned the same bounds. Across the 74 elections, both builds returned byte-identical results in both orders, and the build with the change was about a second faster on a set that takes 51 seconds.
- **Walk a tree into its contests with a lateral join that has an optimization fence, and carry what you need along.** The hex map of an election, `seats.hexes`, walks the election's tree of child elections and reads each one's House or constituency contests. For the 2024 US general election, the tree holds 9,004 elections and 32,171 contests. A plain join from `tree` to `contest` became a nested loop whose join filter threw away 957 million rows. The query now reads each election's contests with `cross join lateral (select ... from contest c where c.election_id = tree.id ... offset 0)`. The tree carries each election's date, so the query no longer joins `election` again. The filter on the area's scheme sits inside the lateral, so area codes are looked up for the 441 House districts instead of for all 17,344 district areas. The two queries behind the map, one for district hexes and one for state hexes, also run at the same time instead of one after the other. For the 2024 US general election, `seats.hexes` went from 21.3 seconds to 3.7 seconds on a cold database and 0.2 seconds on a warm one. For 2022, it went from 18.3 seconds to 1.2 seconds cold and 0.13 seconds warm, and for the 2024 UK general election, from 1.3 seconds to 25 ms warm. The output was byte for byte the same for nine elections and areas.
- **Put a lateral's condition inside the lateral.** `seats.gains` matches a new district to an old one by overlapping shapes only when the district has no predecessor with the same area. That condition sat in the `on` clause of a `left join lateral`, so Postgres ran the shape search for all 441 House districts and then discarded 433 of the results. In the lateral's `where`, the search runs only for the 8 districts that need it. The 2022 US general election went from 12.4 seconds to 3.4 seconds, the 2024 UK general election from 4.0 seconds to 1.5 seconds, and Texas in 2024 from 1.3 seconds to 0.34 seconds, with byte-for-byte the same output.
- **Look up a fixed example by its id, never by its name.** The `/compare` page shows six example pairs. `comparison()` in `apps/web/src/lib/server/pages.ts` used to find each person and party by matching its display name in `name`, which has 9.4 million rows and no index on `text`. That took two sequential scans, and the query took 6.7 to 44 seconds cold. The pairs now name each entity by its id, resolved through `entity_merge` in case the entity has since been merged, and name each polity by its slug path. The query takes 0.12 seconds and returns the same rows.

## Indexes

Every column that a page looks rows up by needs a btree index. The migration `20261031200000_lookup_indexes` added the ones that the plans showed were missing:

- `source_icpsr_idx`, a partial index of the sources whose license mentions ICPSR. The withdrawn-license filter reads it in every result-set query.
- `body_polity_idx`, `office_polity_idx`, `office_body_idx`, `tenure_body_idx`, and `polity_parent_parent_idx`, which polity and body pages use.
- `contest_option_alliance_idx`, a partial index on `(alliance_id, party_id)` for the 1% of options that belong to an alliance. Counting an alliance's wins had read every option of each member party, which took up to 400 ms. It now takes under a millisecond. It is added in migration `20261031230000_alliance_option_index`.

To find another missing index, run the benchmark and then look at `seq_scan` and `seq_tup_read` in `pg_stat_user_tables`.

## Heavy geometry

Some boundaries have more than a million points, Nunavut's among them. Intersecting two such shapes takes seconds. `ea coarse` keeps a simplified copy of every area geometry with more than 20,000 points in `display.coarse`. The tolerance is 0.0002 times the square root of the shape's area. A copy is kept only when it has fewer than half the points and its area is within 0.5% of the original; otherwise the row holds no geometry, and queries fall back to the full shape. `ea tiles` refreshes the table, and rows are dropped when their source geometry changes.

The `coarse()` helper in `archive.ts` returns the simplified copy when one exists. Use it only where a share is measured against the heavy shape itself or against the larger of two shapes, such as overlap with a predecessor district. Don't use it where a share is measured against the smaller shape: simplifying a large neighbor can move a small district's share by much more than 0.5%. Filters such as `&&` and `ST_Intersects` keep using the full geometry.

Across the 70 predecessor pairs of the 12 heaviest districts of Canada's 2025 election, the largest difference between coarse and exact shares was 0.00047. None changed at two decimal places, and none crossed the 1% cutoff for listing a predecessor.

## Rendering and payloads

The server's CPU time matters as much as the database's once the queries are fast. These patterns came out of CPU profiles of cold page loads.

- **Load a country's map with the page.** The page of a country or a supranational body shows a map of its latest general election. The browser used to load it in three requests, one after the other, once the page's scripts ran: `elections.locate` to find the election, then `elections.get` and `seats.hexes` for its results and hex layout. On a repeat visit to `/us`, those requests ran from about 180 ms to 515 ms after the scripts started. The loader in `apps/web/src/routes/[...path]/+page.server.ts` now makes the same three calls on the server and waits up to 150 ms for them. When they finish in time, which they do whenever they are cached, the results go into the page data as plain values. `scrubber.svelte` puts them into the query cache under the keys the map reads, so the browser sends none of the three requests. When they don't finish in time, the page answers anyway and SvelteKit streams the results into the same response when they are ready. The loader doesn't always stream, because Cloudflare never shares a streamed response at the edge (see `mark()` under "The edge cache"). If the results take more than 30 seconds, the stream sends nothing for them and the browser makes the three requests itself. Cloudflare drops a response from the origin that sends nothing for 100 seconds, so the cap keeps a slow election from leaving the map empty. The browser's requests join the computation already running, because the procedure cache in a process shares one pending result per key. Waiting for the whole election without a cap would be a mistake. On its own, the 2024 US general election takes 3 to 5 seconds to compute from a cold cache, but right after a deploy its queries compete for the database with the warm-up and with every other cold page, and a build that waited then sent the first byte of `/us` after 80 seconds. With the cap and a cold election, `/us` sent its first byte in 0.43 seconds and showed its heading after about one second; the map appeared at 31.7 seconds, as soon as the computation finished. Since the hex map's queries were rewritten (see "Walk a tree into its contests" under "Query patterns"), a fresh process with an empty shared cache sends all of the page data for `/us`, map included, in 4.7 seconds instead of 32.4. With the election cached, the map appeared 0.69 seconds after a repeat visit started. The election data adds about 620 KB to the HTML of `/us`, or about 83 KB compressed, the same bytes the browser used to fetch separately. The page text and the Markdown and JSON twins matched the previous build byte for byte for `/us`, `/fr`, `/us/ca`, the 2024 US general election, its presidential contest, and a Los Angeles County contest.
- **Reuse collators and formatters.** `localeCompare` with an options object builds a new ICU collator on every call, which made sorting France's 35,000 communes take 3 seconds. Sort with the shared `natural` comparator in `apps/web/src/lib/format.ts`, which wraps one `Intl.Collator` with numeric ordering. Build number and date formatters with `numbers()` and `dates()` from the same file, which keep one formatter per locale and set of options. Building an `Intl.NumberFormat` takes about 16 µs and an `Intl.DateTimeFormat` about 60 µs, while reusing one takes half a microsecond.
- **Group rows once instead of filtering per row.** When a loop over areas needs each area's result sets, group them with `Map.groupBy` before the loop instead of calling `filter` inside it. Key nested sums by result set, so each set reads only its own entries. On the 2024 UK general election page, the per-area filters took 480 ms of CPU.
- **Send only what the page shows.** A polity page sends the first 20 places of each kind and the 10 largest municipalities, plus the count of each kind. When someone filters the list or asks for every place, the page loads the full list from `polities.get`. The page for France went from 4 MB of HTML to 92 KB.
- **Leave per-race places and maps out of elections with more than 100 races.** `elections.get` gives each race of such an election a `deferred` contest id instead of its places table and map, and the election page fetches them from `elections.race` (`GET /elections/{id}/races/{contest}`) for the race on screen. The race board renders its first 48 cards behind a button that shows the rest, and the page calls `bodies.get` only for the chambers of the races on screen. Washington's 2023 local election went from a 12.7 MB `elections.get` that took 47 seconds cold to 4.9 MB in 7.1 seconds. Its HTML went from 17.3 MB to 4.9 MB, and the browser stopped sending 2,484 `bodies.get` requests, most of which failed with `ERR_INSUFFICIENT_RESOURCES`.
- **Reuse objects that repeat across steps.** SvelteKit's serializer writes an object once when the same object appears in several places. A chamber page's by-election steps each carry the seats of every party, so the loader in `pages.ts` keeps one object per party and seat count, and reuses the nearest-origin map until it changes. It also leaves the raw membership changes out of the page data. The House of Commons page went from 7.3 MB of HTML to 2.2 MB.
- **Pack sparse arrays.** A results map is a matrix with one row per place and one column per party or independent candidate, so most cells are zero or empty. The `transport` hook in `apps/web/src/hooks.ts` encodes every array of 64 or more items where at most a quarter of the items differ from 0 or `null` as its length and the items that differ. It encodes ascending runs of integers, such as the list of columns a place lacks, as start and end pairs. The browser decodes both back to the same arrays, so components never see the encoding. The 2024 UK general election page went from 5.4 MB of HTML to 1.6 MB, or 209 kB compressed, and the 2024 US general election page went from 1.6 MB to 1.1 MB.
- **Send long lists of rows as columns.** Most of a results page's data is lists of same-shaped objects, such as one row per place with the same fields on every row. The `transport` hook also encodes every array of 64 or more plain objects whose rows all have the same keys in the same order, and it stores one list per key. When a list holds only strings, numbers, booleans, `null`, and short arrays of those, the hook sends it as a single JSON string, which the browser reads with `JSON.parse`. Other lists, and arrays of 64 or more items inside them, go through the encoder as usual, so sparse arrays are still packed. The hook skips an array in which the same row appears twice. It also does not send a list as a JSON string when a value is `undefined` or `-0`, or when the same array appears in more than one row. The decoded data then matches the original down to key order and shared objects. The one exception is a row that the page data also holds somewhere else, which would come back as a separate copy. To check, each of 60 pages was serialized again from its decoded data and compared with the original, and none differed; the rendered markup did not change either. Page data for a round of the 2025 New York City mayoral primary by election district went from 2.1 MB to 0.98 MB, and from 371 kB to 162 kB compressed. Its HTML went from 2.0 MB to 1.3 MB.
- **Look up only nearby colors when separating party colors.** `separate` in `archive.ts` gives every party or candidate a color far enough from the colors already placed. Each candidate color used to be measured against every placed color, so an election with 4,000 candidates took 4 seconds. Placed colors now sit in a grid of cells 0.125 wide, larger than the 0.1 distance that counts as far enough, so any color closer than 0.1 is in one of the 27 cells around the candidate. The search stops at the first placed color that is too close to the candidate, or at a distance of zero. The output is identical to the full scan, and the 4,000-candidate case now takes 40 to 300 ms. Each area's list of options is built from the options that got votes there plus the declared ones, instead of filtering every option in the contest for every area.
- **Nest rows with one lookup.** The places list puts each place under the place that contains it. It used to search the whole sorted list for each parent's children, which took 139 ms of main-thread time each time someone switched rounds on the New York City mayoral primary by election district, with about 4,000 places. It now groups the children by parent once with `Map.groupBy`. Together with hover preloading, a switch between rounds went from about one second to about 200 ms from click to painted frame.
- **Keep `:has()` off ancestor elements in global CSS.** In Chrome, a single rule anywhere in the page's stylesheets that tests `:has()` on an ancestor, such as Tailwind's `group-has-*` variants (`:is(:where(.group):has(...) *)`) or `:not(.a:has(.b) *)`, makes every DOM change recheck the styles of the whole document, even when no element on the page matches the rule. Switching rounds on the 2025 New York City mayoral primary recalculated the styles of about 1,600 elements each time. A `:has()` that tests the element the rule styles, such as `has-[>svg]:p-0`, doesn't cause this. The UI components now use a sibling selector (`[[data-slot=command-shortcut]~&]:hidden`) where they need one, and drop the variants that set nothing new. The rules that hide everything but the figure on an embed page moved to `apps/web/src/lib/embed.css`, which the root layout links only when the URL has an `embed` parameter. Style recalculation for each switch between rounds went from about 14 ms to 5 ms on the New York City page by election district and from 38 ms to 13 ms on the 2024 Carlow–Kilkenny count on a phone-width screen, where painting also went from about 110 ms to 78 ms. Those savings match deleting every `:has()` rule from the page. Moving between the 2025 and 2021 primaries also got faster, from about 55 ms of style work to 40 ms. Before adding a `group-has-*` or `in-*` variant with `:has()`, or an ancestor `:has()` in `app.css`, look for a sibling selector or a data attribute that the component can set itself.
- **Skip MapLibre's style validation outside development.** `Map.addLayer` and `Map.addSource` check each new layer or source against the style specification, and to do that MapLibre copies the whole style, with every layer and expression, on every call. The `validateStyle` option of the `Map` constructor doesn't reach these calls. The maps add their fill, hatch, and outline layers again on each round switch, so on the 2024 Carlow–Kilkenny count these copies took 123 ms of the 136 ms spent adding layers. The map engine in `apps/web/src/lib/map/engine.svelte.ts` now adds layers and sources through `map.style` with `validate` set to SvelteKit's `dev` flag, then calls `map._update(true)`, which is what `Map.addLayer` does after adding a layer. `setFilter` gets the same option. The dev server still validates, so a malformed layer still logs an error there. JavaScript time for each round switch went from 214 ms to 110 ms on Carlow–Kilkenny on a phone-width screen and from 148 ms to 124 ms on the New York City primary by election district. The maps draw the same thing as before, and eight map views logged no console errors or warnings.
- **Redraw the basemap only when what it draws changes.** Each round switch hands the map a new contest object, and the map used to fetch the contest's outline again and call `basemap()` with it. `basemap()` used to drop the basemap group and add it back: every land, boundary, and label layer, plus the two basemap tile sources, which made MapLibre reload and reparse the basemap tiles in its workers. `apps/web/src/lib/map/basemap.ts` now stores, for each map engine, the scheme, detail setting, outline, and inset setting it last drew, and returns early when they are the same and the basemap's land layer is still on the map. A theme change doesn't need a redraw, because the engine already sets the paint of every layer again when the theme changes. Measured back to back with the same script, JavaScript time for each round switch went from 92 ms to 58 ms on the 2025 New York City primary by election district and from 74 ms to 37 ms on the 2024 Carlow–Kilkenny count at phone width. Fifteen screenshots of map canvases, including a round switch followed by a switch to dark mode, matched the previous build pixel for pixel, apart from two pixels at the edge of one canvas that were one or two color levels off.
- **Change only the feature states that differ.** The contest map colors each place by setting a feature state on it. `paint` in `apps/web/src/lib/map/engine.svelte.ts` used to clear every feature state of the source and set them all again, so MapLibre rebuilt the paint arrays of every place in every loaded tile on each round switch. It now compares the new states with the ones it painted last. It removes the states of places that are gone, skips places whose state matches key for key, and clears a place's state before setting it only when a key was dropped. A theme change still repaints every place, because it goes through the merged path, which sets every state again. `points` also keeps the JSON of the points it last sent for each source and skips `setData` when it hasn't changed, so the dots and arrows layers no longer go back to MapLibre's worker on every switch. Over 12 switches each on a busy test machine, the median JavaScript time for a round switch went from 107 ms to 40 ms on the New York City primary by election district and from 45 ms to 32 ms on Carlow–Kilkenny at phone width. Time in `setFeatureState` went from 8.5 ms to 0.1 ms per switch, and time in MapLibre's render from 21 ms to 2.4 ms. The 15 map screenshots from the basemap change matched again pixel for pixel. Switching back to the first round, in light or dark mode, drew the same colors as loading that round fresh.
- **Color ID rasters on the GPU and send the full map's data over cacheable GETs.** The full map (`/map/...`, `apps/web/src/lib/atlas/`) colors precincts and counties from raster tiles of area IDs. It used to color them through an `ids://` MapLibre protocol: every recolor and every hover outline bumped a version and called `setTiles`, so MapLibre requested and repainted every raster tile on the main thread. `apps/web/src/lib/map/mosaic.ts` is now a MapLibre custom layer that uploads each ID tile once as an integer texture and colors it in the shader from a small palette texture, so a recolor, hover, selection, filter, or theme change uploads one texture and reloads no tiles. The shader samples the nearest texel, because blending zoom-8 data reads as blur. Past zoom 8, where the rasters end, the real county and precinct shapes fade in from the vector tilesets. Without WebGL2 the old protocol still works. The page also server-renders only a shell and preloads the atlas sheet from `GET /api/v1/contests/{id}/atlas`, which the edge caches, instead of embedding the whole sheet in the HTML. On the 2024 presidential map in headless Chromium at 1440 by 900, the national view went from drawing counties and precincts about 15 seconds after navigation to clearing its loading notice after 3.3 seconds (4.0 seconds at 390 wide). The Georgia map's HTML went from 126 KB to 63 KB gzipped, and the national mosaic is 406 KB gzipped.
- **Read each reactive value once per derived.** Each read of a `$derived` or `$state` value runs a dependency check, so reading one inside a loop or a sort comparator adds up. The `filtered` derived in `apps/web/src/routes/[...path]/places.svelte` read the sort column, the sort direction, the filter, the list of swings, and the shared parts of place names once per row, and it read the column and direction again on every comparison. On the 2025 New York City mayoral primary by election district, with about 4,000 places, that came to tens of thousands of reads per round switch. The derived now copies each value into a local constant at its top. A benchmark ran the old and new derived with Svelte's runtime on that page's data. Recomputing the list after a round switch went from 3.0 ms to 2.0 ms, after a sort from 1.3 ms to 1.1 ms, and after a search from 2.4 ms to 1.4 ms. Both versions returned the same rows for 20 combinations of sort and search. The search also folds accents out of place names only when there is a search, which on its own took the round switch from 3.4 ms to 3.0 ms.
- **Pick the top few rows without sorting them all.** The key places panel on a contest page shows the three closest places, the three largest, and the strongest place for each of the two leading candidates. It used to sort every place once for each list and keep the first few. `best()` in `apps/web/src/routes/[...path]/contest.svelte` now walks the places once and keeps a short sorted list, and the median vote count comes from sorting a `Float64Array`. Tied places come out in the same order as with the stable sort, and the panel picked the same places on the New York City page. With its 4,036 places, building the panel went from 2.7 ms to 0.5 ms per round switch.
- **Fetch once per contest, not once per round.** The contest map fetched the contest's outline in an effect that read the `own` prop. That prop is a new object on every round switch, so each switch sent another `contests.outline` request for the same contest. The response went into deep `$state`, and the basemap's memo key then serialized the outline through Svelte's proxies. The effect now reads the contest's id and tile set through two `$derived` values, which change only when the contest does, and stores the outline with `$state.raw`. The list of outlying places now computes map colors only when the map has outlying or pooled places (such as territories drawn in insets), so most maps compute colors once per switch instead of twice. With the change to the places list above, the median JavaScript time for a round switch over 12 switches went from about 48 ms to 30 ms on the New York City primary by election district, and from about 39 ms to 25 ms on Carlow–Kilkenny at phone width. Map screenshots matched the previous build pixel for pixel. Page text did not change on the New York City primaries, Carlow–Kilkenny, the 2024 presidential election in Pennsylvania and nationally, and Islington North, through round switches, searches, and sorts. On the first pass, the Pennsylvania page seemed to have 64 more characters after every search and sort. Those characters were the map's list of nearby states, which loads after the map's style does, so it was sometimes on the page and sometimes not when the text was read. With that list left out, the text matched the previous build after all 12 steps.
- **Let the browser skip sections that are off screen.** These sections have `content-visibility: auto`: the count table and the places list of a contest page; the seat changes, regional seats, and down-the-ballot sections of an election page; and the results-over-time chart and the elections list of a polity page. While one of them is out of view, the browser doesn't recalculate its styles, lay it out, or paint it, and a round switch only renders the sections someone can see. The property comes on two frames after the section mounts, through the `settle` attachment in `apps/web/src/lib/settle.ts`, which sets `data-settled`. That way, the first render and any jump to `#rounds`, `#places`, or `#down-the-ballot` lay out the whole section as before. `contain-intrinsic-size: auto none` keeps the section's last height, so the page doesn't jump when the section scrolls into view. While a section is skipped, its `innerText` is empty and reading its layout forces a full layout, so check it with `checkVisibility({ contentVisibilityAuto: true })` or wait for the `contentvisibilityautostatechange` event. Don't add the property to a section that holds the place map. On phones, the map's place sheets use `position: fixed`, and the containment that comes with `content-visibility` would pin them to the section instead of the screen. The PNG export sets `content-visibility: visible` on its copy of the figure; without that, the export drew its text in a fallback font. Over 12 switches in the same build, with the property on and off, the median main-thread time for a round switch went from 78.7 ms to 75.7 ms on the New York City primary by election district, and from 67.4 ms to 60.8 ms on Carlow–Kilkenny at phone width. Rendering went from 20.3 ms to 16.0 ms and from 31.9 ms to 23.1 ms. At phone width with the CPU slowed 4×, a full style recalculation after load went from about 100 ms to 35 ms on the 2024 US general election page and from about 148 ms to 111 ms on the 2024 UK general election page; on `/gb` and `/fr` it dropped by 15 to 20 percent. Blocking time during load doesn't change, because the property only comes on after hydration. Once these sections were skipped, computing party colors in TypeScript saved nothing measurable compared with relative color syntax in inline styles: 41 ms against 38 ms with every inline color replaced by a flat one. So the colors stay in CSS.
- **Read layout after the frame, not while Svelte updates the page.** The count strip and the count table scroll to keep the current round in view. They used to read `offsetLeft` and `clientWidth` while Svelte was applying the round switch, which forced a full layout in the middle of the update. SvelteKit then reads the scroll position when the navigation finishes, which forced a second one. The shared `reveal` attachment in `settle.ts` now reads the layout in a `requestAnimationFrame` callback. When the table is skipped because it is off screen, it waits for the table to come into view and scrolls it then. This removed 2.8 ms of `checkVisibility` and 0.5 ms of `offsetLeft` from each switch, and the traces show no forced layout left on the New York City page or on Carlow–Kilkenny at either width. The strip and the table scroll to the same place as before.
- **Cache the narrow-layout check.** `isNarrowLayout()` in `apps/web/src/lib/narrow-layout.svelte.ts` tells the comboboxes, the place switcher, and the map whether to use their phone layout. It used to call `getComputedStyle` and read `clientWidth` on every call, about 10 ms per round switch at phone width on Carlow–Kilkenny. It now keeps the body's width from its `ResizeObserver` entry and the root font size from a `MutationObserver` on the root element's `style`, which is the only place the text size is set. It tells Svelte only when the answer changes. Before the observers report, it reads the layout once as before. The profile of a switch no longer shows it, and the comboboxes still open as a drawer at 390 pixels and as a popover at 1,280, switch when the window is resized, and follow a larger text size.
- **Test each map color once.** The contest map draws places whose leader has a gray color at full strength instead of shading them by margin. `fills()` in `map.svelte` used to parse the computed color for every place to find out whether it was gray. It now keeps the answer for each color during a paint.
- **Load the overlays when the browser is idle.** Every page used to ship the code for four overlays that most visits never open: the toast area, the confirmation dialog, the source popover that opens when someone clicks a number, and the term explainer. They pulled in svelte-sonner and the popover and drawer components, so they cost about 40 KB of compressed JavaScript before the page could respond. `apps/web/src/lib/components/overlays.svelte` now holds all four, and the root layout imports it with `requestIdleCallback`, or after 300 ms in browsers without it. The stores that open the overlays still load with the page, so a click on a number before the overlays arrive opens the popover as soon as they load. The footer's Shahmaran mark was a Svelte component with a 22 KB path, so the path was in every page's HTML and in the root layout's script. It is now `apps/web/static/shahmaran.svg`, which the footer uses as a CSS mask over the text color, so the browser fetches it once and caches it. The JavaScript a page loads before it can respond went from 213 KB to 171 KB compressed with Brotli, from 83 files to 74, and from 692 KB to 548 KB uncompressed. The CSS went from 31.4 KB to 29.3 KB compressed. In a headless browser, the source popover opened with its source, closed on Escape, and returned focus to the number; at phone width it opened as a drawer. The footer mark kept its size, angle, and opacity.
- **Merge classes in one place.** `tailwind-variants` builds the class names of the button and input group components. Its default entry point bundles its own copy of a class-merging engine, about 30 KB uncompressed, which every page loaded alongside `cn`, the merger the app uses everywhere else. Every variant function's result already passes through `cn` together with the component's `class` prop, so the three components now import `tv` from `tailwind-variants/lite`, which joins the classes without merging them, and `cn` does the merging once. A script compared the old and new class strings for every combination of variant and size with each of the 36 `class` values that the app passes to these components, 2,628 cases in all, and none differed. The class attributes in the server-rendered HTML of nine pages also matched. The JavaScript a page loads before it can respond went from 171 KB to 163 KB compressed with Brotli, and from 548 KB to 519 KB uncompressed.
- **Load the header's menus when the browser is idle.** The header's theme menu, account menu, and phone-width drawer brought bits-ui's menu and dialog code, vaul, and the segmented control and switch from the drawer into every page's first load, though few visits open them. `apps/web/src/lib/components/header-menus.svelte` now holds the three menus, and the header loads it with the same `idle()` helper in `apps/web/src/lib/idle.ts` that loads the overlays. Until it arrives, the header renders the same trigger buttons from shared snippets, so the server-rendered header matches the old one apart from bits-ui's own trigger attributes. A click on a trigger before the menus load opens that menu once they arrive, and a trigger that has keyboard focus when the menus arrive passes the focus to the real trigger. The JavaScript that a page loads before it can respond went from 163 KB to 133 KB compressed with Brotli, from 74 files to 64, and from 519 KB to 400 KB uncompressed. In a headless browser with the menus' file held back, the theme menu and the drawer each opened when clicked before the file arrived, focus moved from a placeholder to the real trigger, and the drawer closed after following one of its links.

Page text did not change through round switches, searches, and sorts on the same pages as above, at 1,280 and 390 pixels wide, and the Markdown and JSON twins matched. This time the old and new builds ran side by side on the staging server and were read at the same moment. Text recorded an hour earlier on the old build differed by 14 characters on three pages, because the data had changed in the meantime.

- **Give the web fonts fallbacks that take the same space.** The site's text faces, Sofia Sans Semi Condensed and Piazzolla, load with `font-display: swap`, so the browser first draws text in a system font and redraws it when the font file arrives. The system fonts were wider or narrower than ours, so the swap rewrapped lines and moved everything below them. `apps/web/src/app.css` now declares four fallback faces, a regular and a bold for each family, over Arial and Times New Roman, or Liberation Sans and Liberation Serif where those are missing. Each face sets `size-adjust` so that its average letter width, weighted by English letter frequency, matches ours at weight 400 or 700, and sets `ascent-override`, `descent-override`, and `line-gap-override` so that its line height matches too. The values came from the font files, read with fontTools. The fallback faces cover only the Latin range of our subset files, because Arial also has Arabic letters and Arabic text should still fall back to Noto Naskh. `apps/web/src/hooks.server.ts` also preloads the Latin Sofia file, which every page uses, through SvelteKit's `preload` option, so the browser asks for it alongside the scripts instead of after it parses the CSS. Preloading the Latin Piazzolla file as well made the largest paint of a contest page about 24 ms later, because that paint is Piazzolla text and the preload competed with the page's other files, so only Sofia is preloaded.
- **Send a polity's record with the page.** The page of a country or a supranational body shows a "Results over time" panel, and the scrubber, the timeline, and the offices list all read the polity's record from `polities.record`. The browser used to fetch the record after the page's scripts ran, which took 107 KB uncompressed for the United Kingdom and 189 KB for the United States, and the panel grew by about 180 pixels when it arrived. The loader in `apps/web/src/routes/[...path]/+page.server.ts` now makes that call on the server, with the same 150 ms wait as the map's data, through a shared `soon()` helper. `polity.svelte` puts the record into the query cache, or prefetches it from the streamed promise when the wait runs out. The scrubber also used to fetch the elections on either side of the current one as soon as it mounted, about 150 KB over the network for the 2019 UK election alone. It now waits until someone points at the panel or moves focus into it.

Together, these two changes removed layout shift from the pages measured. The old and new builds ran side by side against the same database, and each page loaded 7 times per build in alternation, at 390 pixels wide with the CPU slowed four times and a 9 Mbit/s connection. The table gives the medians.

| Page           | Layout shift, old → new | Blocking time, old → new | Largest paint, old → new |
| -------------- | ----------------------- | ------------------------ | ------------------------ |
| `/gb`          | 0.185 → 0               | 760 → 819 ms             | 380 → 392 ms             |
| `/fr`          | 0.143 → 0               | 466 → 534 ms             | 344 → 376 ms             |
| `/us`          | 0.156 → 0               | 710 → 839 ms             | 344 → 392 ms             |
| `/de`          | 0.173 → 0               | 432 → 530 ms             | 344 → 372 ms             |

After the load event, the old build requested `polities.record`, `elections.locate`, and `elections.get` on the four polity pages, and the new build requests none of them. The cost is that the record's panels are now in the server-rendered HTML and hydrate with the rest of the page, which adds 60 to 130 ms of blocking time and up to 50 ms to the largest paint on polity pages under this throttling. The HTML grew by 22 to 26 KB compressed on the country pages and 11 KB on `/us/ca`, and most of that is the seat chart, which draws about 400 bytes per seat. The page text matched the previous build on `/gb`, `/us`, `/fr`, `/de`, `/tr`, `/us/ca`, and Aldershot 2024 at 1,280 and 390 pixels wide, and their Markdown and JSON twins matched byte for byte.

- **Stream a local election's winners.** A local election with 40 or more places lists each place's winners, and a layered mayoral election, such as one of Turkey's local elections, opens with a sweep of winner maps. The loader in `apps/web/src/lib/server/pages.ts` used to wait for `elections.winners` before it answered. With a cold cache, that call took about 20 seconds in production for the 2019 Turkish local elections and 6.6 seconds on ea-dev, close to the point where Cloudflare gives up on the origin. The loader now passes it through `soon()`, which moved there from `+page.server.ts` so every loader can use it, and through `capped()`, which gives up after 30 seconds and lets the browser fetch the data itself. The page has to decide whether to lay out the sweep before the winners arrive, so the loader runs a quick query in their place: an election counts as mayoral when at least nine in ten of its child elections have a mayor's contest. Across all 166 local elections with 40 or more children, this matched the sweep exactly: the 13 Turkish local elections. While the winners stream, a skeleton one screen tall holds the sweep's place, and `election.svelte` puts the winners into the query cache when they arrive. A contest's map of council winners, such as the one on the mayors' page of a Turkish local election, streams the same way. The Markdown and JSON twins still wait for the winners. On ea-dev with a cold cache, `/tr/2019-03-31-local` now sends its first byte after 4.1 seconds, which is the time `elections.get` takes, and the mayors' page sends its first byte after 7.9 seconds instead of waiting for a 12.2-second winners call on top of the contest. The page text and both twins matched the previous build on the hub, the 2024 UK general election, a Los Angeles County contest, the 2019 and 2024 Turkish local elections, the 2019 mayors' page, `/us`, and the 2024 US general election.

- **Write less markup per seat.** The parliament chart in `apps/web/src/routes/[...path]/seats.svelte` draws one `<circle>` per seat, and each one used to take about 400 bytes: coordinates with 15 decimal places, five animation and transition classes, and the party's full `light-dark(oklch(from …))` fill. The chart now rounds seat positions to hundredths and the dot radius to thousandths of a viewBox unit, and the classes that every seat shares sit once on the `<svg>` as `[&>circle]:` variants. A seat now takes about 260 bytes. The seat chart on `/gb` went from 262,878 to 167,559 characters, and the server-rendered HTML went from 1,648 KB to 1,553 KB raw and from 170.9 KB to 166.3 KB with Brotli. On the other polity pages the HTML shrank by 6 to 16% raw and by 3 to 11% with Brotli. The largest drop was on `/tr` (41.1 KB to 36.5 KB). A script compared every seat's id, label, selection state, computed fill and stroke, radius, position, animation, and transform origin in the old and new builds, at rest and on hover, in light and dark mode, with and without reduced motion, on eight pages, and none differed. The Markdown and JSON versions of nine pages matched byte for byte. We also tried setting each party's color once as a custom property on the `<svg>` and filling seats with `var(--seat-N)`, which saved another 2 to 4% of the HTML. It added 50 to 90 ms of blocking time on every polity page, because the browser substitutes the variable and parses the relative color again for each seat, so the fills stay inline. We measured through a Brotli proxy, as production serves the HTML, at 390 pixels wide with the CPU slowed four times and a 9 Mbit/s connection, with 7 loads per build in each order. Blocking time was the same or lower on 11 of 12 runs, by up to 6%. The largest paint moved by amounts in both directions that were within the noise. Build the old and new versions in a tree that holds no other build output: Tailwind scans every file it finds under `apps/web`, so a `build-old` folder there adds class names from its JavaScript to the render-blocking CSS and makes the new build look slower.
- **Don't read layout while the page hydrates.** `isNarrowLayout()` in `apps/web/src/lib/narrow-layout.svelte.ts` used to answer its first call with `document.body.clientWidth` and the root's computed font size. The map and the place switcher call it while the page hydrates, so the browser had to stop, recompute the style of every element, and lay out the page, and then do it again once hydration finished. On `/us/2024-11-05-general` the forced recalculation took 236 ms on a phone. The first answer now comes from `matchMedia`, scaled by the percentage that `app.html` writes to the root's inline font size. The `ResizeObserver` reads the computed size later, after layout has run, when the read costs nothing.
- **Don't let mode-watcher disable transitions on load.** By default `ModeWatcher` turns off every transition whenever the mode is applied. It adds a `* { transition: none !important }` style element and removes it a frame later. On page load it ran that up to three times, and each insertion and removal made the browser recompute the style of every element on the page, which took about 115 ms each on `/us/2024-11-05-general`. `+layout.svelte` now passes `disableTransitions` only after the first `pointerdown` or `keydown`, so a theme the reader picks still switches without transitions.

  Together the two changes lowered the median blocking time under the throttling in "Measuring" by 20 to 45 percent: from 930 to 608 ms on `/us/2024-11-05-general`, 890 to 575 ms on `/gb`, 586 to 358 ms on `/tr`, 565 to 311 ms on `/de`, 681 to 387 ms on `/fr`, and 963 to 774 ms on `/us`. The largest paint did not change beyond measurement noise. That more than recovers the 60 to 130 ms that hydrating the record's panels added to polity pages.

- **Find what triggers a style recalculation.** Record a trace with the `disabled-by-default-devtools.timeline.invalidationTracking` and `disabled-by-default-devtools.timeline.stack` categories. Each `UpdateLayoutTree` or `Layout` event over about 30 ms then carries the stack that forced it and the invalidations behind it. A forced one inside hydration, or a "Style rule change" from a style element added and removed, is worth removing. The SvelteKit client's own read of the scroll position before hydration also forces layout, but that layout is the page's first and would run anyway.

## Live results pages

A live election page, such as `/live/us/2026-11-03-general`, loads the election through the `live.election` procedure, which is cached per update stamp, plus the maps and seat counts it shows. On a server with an empty cache, the national page's data used to take 8.2 seconds and 183 KB gzipped. The query and payload changes below brought it to 1.7 seconds and 142 KB, and moving the House map to its own request, 33 KB gzipped, brings the page data down to 110 KB. A state page's data takes 0.5 to 1.3 seconds.

- **Cache the parts of an election that don't change during the count.** Each new update stamp recomputes the election, but most of what it reads stays the same all night: the options on each ballot, the incumbents, the certified contests, the baselines from earlier elections, the map geometry, and the jurisdictions. `live.election` keeps these under `live:fixed:v1:{path}|{rest}|{detail}` with `remember()`, so a new stamp only reads the data that changes with each count.
- **Load the page and its ballot at the same time.** The live page route runs `livePage()` and `liveBallot()` together, and each one runs its own independent queries with `Promise.all`.
- **Find sitting officeholders with one pass over current tenures.** `control()` used to run a lateral lookup per contest that tested seats, offices, and district codes with `or` and an `exists`. It now selects the current tenures once, joins them to the contests by seat, by office, and by district area in three branches of a `union all`, and keeps the latest per contest with `distinct on`.
- **Isolate the reporting-unit lookup when totaling turnout.** The totals in `load()` map each unit to its county inside a `cross join lateral (... offset 0)`, which keeps the planner from reading every reporting unit. This took the query from 160 ms to 49 ms per state.
- **Test district contests with `exists` instead of joining and deduplicating.** `house()` selects the congressional districts that have a contest in the election with an `exists` subquery, instead of joining every contest and running `distinct`.
- **Load the House map only when the page can show it.** The national page opens on the Senate view, and its House map, district codes, and cartogram were about a fifth of its data. The dashboard fetches them from `/live/house/{path}` when the browser goes idle, or right away when someone opens the House view.
- **Write cartogram paths in compact relative form.** `ea cartograms` writes each outline as relative SVG commands in hundredths, with `h` and `v` for straight edges, implicit repeated commands, and no redundant zeros or spaces, such as `M1.73 44l-.86.5-.87-.5-.87.5v1l.87.5h.87z`. Every path decodes to the same points as before. The US and UK layout files went from 23.4 MB to 14.3 MB.
- **Share one object per party.** Every option of the same party points to the same party object, so SvelteKit's serializer sends each party once.
- **Round baselines to what the page can show.** Baseline shares are rounded to six decimal places and expected votes to whole votes. This changes the values the page receives by at most 0.0000005 and half a vote, and it saves about 18 KB gzipped on a large state's data.
- **Measure rows in batches.** The windowed list measures the rows it renders in one microtask instead of once per row.

The warm-up script requests the live page of every general election from a week before today to two weeks after, national pages first, so the first visitor after a deploy doesn't pay for these queries. That covers the country and every state, district, and territory under it. For each page it also requests the map shapes, and it requests the House map for the national page and the local ballot for each state page, because the browser asks for those as soon as the page loads. Cold, these took 1.0 s for the House map, 0.6 s for the national map shapes, and up to 0.6 s for a state's ballot. A local hub or race page takes 30 to 100 ms cold, so the warm-up leaves the roughly 50,000 local pages of a November general to their first visitors.

The server keeps each live page's latest computed answer in memory until the next update. National and state pages keep theirs in a map with no limit, while local hubs and races share a map capped at 64 entries. Before, they shared one map, and a stream of visits to local races pushed the state pages out, so each state page was computed again even when no new count had arrived. Each entry is keyed by the election's resolved path, so variant spellings of a path, such as doubled slashes, share one entry.

## Checking a change

A performance change must not change what a page says. Before each one is committed, it runs on a staging server, and the same requests go to the old build and to the new one: the places and JSON twin of a nomination hub, of a presidential general election, and of a county-level contest, plus whatever endpoints call the changed query. Each request changes the case of the letters in its ids, so it gets past every cache and runs the query again. Any difference between the old and new responses counts as a bug unless the change was meant to make it. For a query rewrite, the old and new queries also run directly against the database over a hundred or more real inputs, and their rows must match.

When comparing page text before and after a frontend change, wait until the parts that load after the page does are on the page, such as the map's list of nearby places, or leave them out of the comparison. Otherwise a difference in timing looks like a difference in content.

Procedures lowercase ids after the cache lookup, so a request with changed case still misses the cache but gets the same names and paths as the lowercase request. Before this, a polity, election, or chamber requested with an uppercase id came back with an empty name.

## Measuring

The benchmark we track requests 45 representative pages one at a time against the origin, first with every cache empty and then with both tiers warm.

| Change                                                                                      | All 45 pages, cold | Slowest contest page, cold |
| ------------------------------------------------------------------------------------------- | ------------------ | -------------------------- |
| Before                                                                                      | 98.7 s             | 34 s                       |
| JIT off, lateral result-set lookups, lookup indexes, and the turnout rewrite                | 91.4 s             | 13.7 s                     |
| zstd, the owner predicate, and the recursive-CTE rewrites                                   | 80.8 s             | 13.2 s                     |
| Coarse geometry for overlaps                                                                | 69.0 s             | 3.0 s                      |
| Geometry-first lookups, lookups for lateral rollups, and the six lookup indexes             | 61.6 s             | 2.85 s                     |
| Intersects guards, grouped district lookups, and decided-race shortcuts                     | 57.4 s             | 2.83 s                     |
| Memoized path resolution, indexable peer joins, the ballot prefilter, and streamed sections | 54.7 s             | 2.72 s                     |

With both cache tiers warm, all 45 pages take 1.9 s together, and the slowest takes 0.34 s.

Pages below the county level gain the most from memoization and streaming. A Cleveland precinct page in the 2016 Ohio Senate race took 25.1 s cold. It now sends its first byte after 2.2 s and finishes streaming after about 6 s. The next precinct in the same district sends its first byte after 0.8 s. A Canadian riding opened from the national map takes 1.8 s cold, where it took more than 20 s before.

Polity and election pages with thousands of places gained the most from the rendering changes. France's polity page took 4.2 s cold and now takes 2.1 s. The 2024 UK general election page took 3.7 s and now takes 3.3 s. With the cache warm, both take under 0.15 s.

Most of the remaining cold time goes to reading from disk, because the database is about as large as the server's memory. The two slowest queries left are geometric. One draws the home page's world map, and its output is the same for every request, so the warm-up run caches it. The other query measures how much of a heavy district its predecessor covers, which means intersecting two shapes of about 90,000 points each. Pre-simplifying the world map changed its output, and btree indexes on `area_parent (area_id)` and `election (date_from, kind)` saved less than 10% on warm queries, so neither change was made.

The origin answers a cached request in under 10 ms, but the edge adds most of the time a visitor waits. From the US east coast, a cached contest response takes about 0.15 s when the Cloudflare machine that takes the request already has an open connection to the origin in Germany, and longer when it has to open one. With little traffic, between one in ten and one in four requests open a new connection.

Opening a connection used to cost three round trips across the Atlantic instead of two. Cloudflare's TLS handshake to the origin listed the post-quantum group X25519MLKEM768 as supported but sent key shares only for X25519 and an older Kyber draft. The origin's TLS library prefers X25519MLKEM768 and does not implement the draft, so it answered every new connection with a HelloRetryRequest. Turning off Cloudflare's post-quantum setting for origin connections removed that round trip. A request on a new connection now reaches the origin about 210 ms after the first packet instead of about 310 ms, and the slow requests fell from a median of 0.47 s to 0.37 s across 468 timed requests. The hop from Cloudflare to the origin now uses X25519 alone; it can go back to post-quantum once Cloudflare sends an X25519MLKEM768 key share. A Cloudflare Tunnel was also tried, and it was slower: about half of its requests took 0.3 s, for a mean of 0.23 s against 0.16 s for a direct connection.
