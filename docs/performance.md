# Performance

This page explains how the site stays fast: where results are cached, how the cache is kept warm, which database settings matter, and which query patterns we use and avoid. Read it before you write a new RPC query or change the cache.

## How a page is served

Cloudflare sits in front of the origin and caches what the origin marks as shareable (see [The edge cache](#the-edge-cache)). Static assets under `/_app/immutable/` have content-hashed names and are sent with `cache-control: public, max-age=31536000, immutable`, so browsers and the edge keep them for a year. Pages and twins are rendered by the SvelteKit server, which answers each page from a handful of RPC procedures called in-process. A loader starts independent procedure calls together with `Promise.all`, so a contest page waits for its slowest call, not for the sum of them.

Each kind of archive page (contest, election, day, and polity) is its own JavaScript chunk, loaded with a dynamic `import()`, so a contest page doesn't download the code for the other three. That cut the JavaScript a contest page preloads from about 473 kB to 240 kB gzipped.

Two sections of the contest page, the ballot list and the lean chart, sit below the results and can take seconds on a cold cache. They don't hold up the page. The loader starts them once the contest is found. When the main data is ready, it returns each one as a plain value if it has already finished, and as a promise if it hasn't. SvelteKit streams a promise to the browser when it resolves, and the page renders it with `{#await}`. A warm page therefore arrives fully rendered, and a cold one shows the results first and fills in the rest. The Markdown and JSON twins wait for both.

## The edge cache

Cloudflare caches every response that the origin marks as shareable. `mark()` in `apps/web/src/lib/server/edge.ts` determines this as each response leaves the server. A response is shareable when it answers a GET or HEAD with a 200, sets no `cache-control` or `set-cookie` of its own, goes to a visitor who is not signed in and sent no `authorization` or `x-api-key` header, and is not under `/api/auth`, `/mcp`, or `/rpc`. A shareable response gets two headers:

- `cache-control: no-cache`, so browsers keep the page but ask the edge before reusing it. The edge answers with a 304 when the page hasn't changed.
- `cloudflare-cdn-cache-control: public, max-age=300, stale-while-revalidate=86400, stale-if-error=86400`, which only Cloudflare reads and never passes on. The edge serves its copy for five minutes. After that it keeps serving the old copy while it fetches a new one in the background, and if the origin fails, it serves the old copy for up to a day.

Every other response gets `private, no-cache` unless it already set its own `cache-control`, so the edge never stores it.

Page data is shared the same way, with one more check. When someone moves between pages, or between the rounds of a count, the browser fetches the new page's data as `__data.json`. SvelteKit marks every data response `private, no-store`, and it reports a load error inside a 200 instead of with an error status. So `mark()` reads the body of each data response and shares it only when it is plain JSON that starts as page data and holds no error node. A streamed response, a redirect, or a load error keeps SvelteKit's `private, no-store`. A shared data response also gets an ETag, a hash of its body, so a browser that goes back to a round it has already seen gets a 304 from the edge instead of the whole response. On the 2025 New York City Democratic primary for mayor, by election district, a round's data used to come from the origin every time: about 0.3 seconds when the origin was idle, and 1.3 to 1.9 seconds while the warm-up was running. From the edge it takes about 0.15 seconds, and a click on a round paints in 0.3 to 0.47 seconds. The edge compresses a cached copy less tightly than a response that it passes through: browsers that accept zstd get about 371 KB either way, while browsers that accept only brotli get about 360 KB instead of 263 KB.

Live results get a much shorter edge lifetime: `public, max-age=5, stale-while-revalidate=10, stale-if-error=3600`. This covers live pages, their twins, their page data, the live API, and `live.stamp`, the update check that an open live page sends every 30 seconds as a GET. A visitor sees a count at most about 15 seconds older than the origin's, and however many people are watching, the origin answers each of these URLs only once every few seconds per Cloudflare data center. If the origin goes down, the edge keeps serving the last count for up to an hour. Live page data skips the error check that other page data goes through, since a cached error lasts only a few seconds. Live responses that aren't shareable send `no-store`.

The edge keeps one copy of each URL per format and per locale. A page and its Markdown and JSON twins share a URL and differ only by the `Accept` header, so a cache rule sorts each request into `text/html`, `text/markdown`, or `application/json`. The locale comes only from the `PARAGLIDE_LOCALE` cookie, never from the URL or from `Accept-Language`. Before the cache lookup, a transform rule copies that cookie into an `x-locale` request header, and shareable responses send `vary: accept, x-locale`. A response is shareable only when `x-locale` matches the cookie and names a known locale, so a forged header or an unknown locale can't put a page into another locale's copy. Because a cached page can't depend on the browser's language, the site doesn't pick a locale from `Accept-Language`. A banner will suggest one instead once a second locale ships.

Requests that carry a session cookie, an `authorization` header, or an `x-api-key` header skip the edge cache entirely: a cache rule matches them before the lookup. The origin also marks those responses private, in case a rule is ever wrong.

When a new build starts, the server purges the edge cache for its own host through the Cloudflare API. It records the build in Redis, so restarts and extra instances of the same build don't purge again. The purge needs `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_PURGE_TOKEN`, an API token that can only purge the cache of that zone; without them the server skips it. Between deploys, a publish reaches visitors within about five minutes, as edge copies expire.

Cloudflare's tiered cache is on, with smart topology. A data center that misses sends the request to an upper-tier data center before the origin, and the upper tier keeps warm connections to the origin. A miss in the eastern United States for France's polity page took about 450 ms past the TLS handshake when every data center went to the origin on its own; through the upper tier it takes about 180 ms, and a hit takes about 50 ms. Every `Accept-Encoding` value shares one edge copy, because the edge compresses each response itself, so one request primes a page for every browser.

Cloudflare keeps the origin's ETag only when no zone feature rewrites the HTML, so Email Obfuscation, Automatic HTTPS Rewrites, Replace insecure JavaScript libraries, Rocket Loader, and injected bot-detection scripts stay off. When Cloudflare compresses a page itself, it turns the ETag into a weak one, which still gets a 304 when the browser checks.

## The procedure cache

Every read procedure goes through `remember()` in `apps/web/src/lib/server/cache.ts`. A result is keyed by the procedure's name and its JSON input, and it lives in two tiers:

- **In-process.** A `Map` used as an LRU, capped at 20,000 entries or 1 GiB of serialized size, whichever comes first.
- **Shared.** Redis, keyed by `c:<build>:<procedure>:<input>`. Values are serialized with `node:v8`, compressed with zstd, and kept for 30 days. Values larger than 64 MiB are not stored.

The build id in the key means a deploy never reads results written by older code, so every deploy starts with an empty shared cache.

Each entry carries the data version that was current when it was computed. The version joins today's date, the number of published and rejected changesets, the time of the latest publish, and the time of the latest coverage build. The server reads it at most every five seconds. When the version moves, a stale entry is still served right away and a background renewal recomputes it. At most four renewals run at once, so the database never gets a burst of heavy queries after a publish. Procedures built with `strict` instead of `os` never serve a stale value: they recompute before answering.

## Warming

Because a deploy empties the shared cache, the first visitor to each page would pay for every query. After each deploy and each database restore, a warm-up script asks the database for the pages people are most likely to open: the home page, every country, supranational body, and federal unit, their recent general elections, and every contest in each one's latest general election. That is about 18,000 pages. The script requests each page three at a time from the origin, which fills both cache tiers in about 35 minutes. It then requests the same pages through the public hostname, which puts each one in Cloudflare's upper tier, so a visitor anywhere gets a page that is already at the edge.

A contest counted in rounds, such as a ranked-choice or single transferable vote count, has one page per round, and only `contests.get` reads the round. When someone opens one round, the server computes the contest's other rounds in the background after it answers, one after another: the next round, the previous round, and the final round first, then the rest from nearest to farthest, up to 12 rounds in all. No more than two pages warm their rounds at once, so a burst of visitors cannot pile heavy queries onto the database. In the browser, the round links in the count table preload on hover instead of on tap. On the 2021 New York City Democratic primary for mayor, by election district, the first round took 6.5 seconds cold, and 30 seconds later every other round took 0.4 to 0.55 seconds.

Inside `contests.get`, the queries that don't depend on the round are shared across a contest's rounds: the result sets picked for each place, the covering contests, the channel pools, and the name of the finer level. Each one is cached under a key built from its own inputs, with `across()` in `archive.ts`. These entries are strict, so a page recomputed after a publish never reads one of them stale. Only contests counted in rounds use them, which keeps the in-process cache from filling with entries no other page would read. A cold round of the 2021 primary went from 4.7 seconds to 3.4 seconds, and its database time from 3.7 seconds to 1.9 seconds.

The round's own results are split the same way. For a round, `load()` reads only that round's rows, and the database drops the other rounds inside the index scan instead of reading them. What depends on every round comes from a frame that `stepped()` caches for each set of picked result sets and areas: each area's main measure, the result sets and areas that report it, and the totals that order the options. The options that have no votes in a round are found once per result set for all of its rounds, instead of once for each of the ten or so loads that a single round makes. The label points for the map are cached by their areas and date. A cold round of the 2021 primary now takes 1.2 seconds, 0.4 seconds of it in the database. A cold round of the 2025 primary by election district went from 1.3 to 1.7 seconds, down to 0.75 to 0.97 seconds. Most of what remains is building and sending the response, which is 1.6 MB, or 136 KB compressed.

## Database settings

- **JIT is off.** Our queries are large and generated, and their plans are expensive to compile. With JIT on, one contest page spent 14 of its 34 seconds compiling.
- `random_page_cost = 1.1` and `effective_io_concurrency = 200`, which suit SSD storage.
- After a restore, `vacuumdb --freeze --analyze` runs with eight jobs. Freezing sets the visibility map, so index-only scans skip the heap, and analyzing gives the planner fresh statistics.
- The web pool holds up to 32 connections and waits up to 30 seconds for one.
- `pg_stat_statements` and `track_io_timing` are on. Rank `pg_stat_statements` by `total_exec_time` to find the next query to fix.

## Query patterns

These patterns came out of plans that read whole tables. Each one turned a query that took seconds into one that takes milliseconds.

- **Start from a small set of ids.** When a query needs rows for a few contests, select the ids first, then fetch rows with `cross join lateral (select ... where rs.contest_id = ids.id offset 0)`. The `offset 0` keeps the planner from flattening the subquery into a hash join over the whole table.
- **Don't join recursive CTE output back to big tables.** Postgres estimates recursive CTEs poorly, so a join from `grp` or `tree` back to `contest` or `election` often becomes a hash join over all of `contest` (about 950,000 rows) or `election` (about 220,000 rows). Fetch the extra columns with a scalar subquery or a lateral instead.
- **Use `= any(array[x])` when an equality would pick the wrong index.** When a column is indexed by a btree and also appears, not first, in a GiST key, a plain equality can lead the planner to the GiST index. `= any(array[x])` steers it to the btree.
- **Don't wrap indexed columns in `coalesce`.** Write `(c.body_id = x or (c.body_id is null and c.office_id = x))`, not `coalesce(c.body_id, c.office_id) = x`, so each branch can use its index.
- **Filter before joining territories.** Find the elections you need first, then join `polity_territory` for only those.
- **Test existence in a select list with `(select true ... limit 1)`.** The planner can turn an `exists` in a select list into a hashed subplan that reads every matching row in the table. A scalar subquery with `limit 1` always runs per row and stops at the first match.
- **Probe geometry through its spatial index first.** Select candidate shapes with `g.geom && ST_MakeEnvelope(...)` in a subquery that ends in `offset 0`, then join `area` and filter by date. Without the optimization fence, the planner can combine the spatial index with the date index in a bitmap AND that reads hundreds of thousands of rows.
- **Fix the leading column of a GiST key.** The keys of `area_geometry`, `area_parent`, and `reporting_unit_area` are GiST indexes on an id and a `valid` range. A probe that fixes only the date scans the whole index. Start from the ids you already have, and look up each one with a lateral subquery.
- **Compute constant sets once.** Put a filter that doesn't depend on the row, such as the list of ICPSR sources or the dates of elections that have polity-wide results, in `= any(array(select ...))` or a materialized CTE. Then it runs once per query instead of once per row.
- **Summarize a CTE once, not once per row.** A scalar subquery such as `(select id from ahead a where a.root = i.id order by a.depth desc limit 1)` reads the whole CTE for every row. Compute `distinct on (root)` once and join the result.
- **Group before you test.** When thousands of rows collapse to a few hundred keys, as when every past contest of a body maps to its districts, group by the key first and run the existence checks on the grouped rows.
- **Fetch notes by entity id.** Put the union of ids first, then fetch matching rows with a lateral lookup by `entity_id`, instead of testing `exists` against the union for every note.
- **Run cheap geometry tests before expensive ones.** Compare bounding boxes with `&&`, or check `ST_Intersects`, before computing `ST_Intersection`. Fold "has no shape" and "overlaps" into one lookup per row instead of two. Clip a heavy shape to the other shape's bounding box with `ST_ClipByBox2D`, wrapped in `ST_MakeValid`, before intersecting them.
- **Make `is not distinct from` joins indexable.** A join on `c.body_id is not distinct from me.body_id` can't use an index. When one side is known to be non-null, add `(c.body_id = me.body_id or c.office_id = me.office_id)` so the planner can probe both indexes, and keep the null-safe test as a filter. For a small constant set, use `= any(array[...])`.
- **Memoize shared helpers.** A contest page runs several procedures, and each one resolves the URL path through `children()`. `children()` and the lean atlases also go through `remember()`, so a page load resolves each path once, and concurrent calls share one query.
- **Rule out candidates before resolving them.** The ballot list checks every contest held in the same place on the same day. A cheap check drops the contests that can't list this place before the expensive path resolution runs: it checks whether the two shapes' bounding boxes overlap, whether the place sits under the contest's area, and whether reporting units link them. On a Cleveland precinct page, the test dropped 112 of 133 candidates, and the ballot went from 20 s to 5 s cold.
- **Split an `or` across different tables into a `union all`.** A filter such as `ct.entity_id = x or ct.entity_id in (select ...)` can't use one index for both branches, so the planner reads every citation. Select each branch on its own and combine them with `union all`; each branch then uses its own index.
- **Compute once per election day, then read per contest.** Many contests share a day, a kind of election, and the areas they report in. Turnout by place is computed for every area of a day and kind, cached under that day and kind, and then filtered to the areas one contest needs. In the same way, a contest map walks a state's areas once per level and day, and reads inset parts once per boundary scheme and day. The first contest of a day pays for the query, and every other contest that day reads the cached result.
- **Start from the smaller side, and decide which side in TypeScript.** Before a contest page looks up the areas below its top areas, a quick count compares the top areas' children with the areas that have results. If the top areas have no children, the lookup is skipped. If fewer areas have results than there are children, the query starts from the areas with results. Make this choice in TypeScript with two queries, not in SQL with a `union` of both directions: `result_value` has 35 partitions, and planning both branches costs more than the branch saves.
- **Look up related rows by their own index.** To find each contest's runoffs, don't group every runoff in the database in a CTE and join it back. Use a lateral subquery per contest, `where n.previous_round_id = c.id`, which reads only that contest's runoffs. Fetch a contest's election the same way, with `cross join lateral (select ... from election x where x.id = c.election_id offset 0)`. On the race list of an election page, this took the query from 107 ms to 3 ms. Resolve merged parties the same way, with a lateral lookup into `entity_merge` by id.
- **Start a slow query as soon as its inputs are known.** Inside `contests.get`, the query for the contests that cover the same place takes 300 to 500 ms cold, and it needs only the contest, its area, its path, and its number of rounds. It used to wait behind about a dozen smaller queries that don't feed it. It now starts as soon as those inputs are known and runs alongside them, and the two small queries that follow it run at the same time as it does. Attach `.catch(() => null)` to a promise you start early, the way `county`, `overall`, and `covers` do. Then an error thrown before the `await` doesn't crash the process as an unhandled rejection, and the later `await` still sees the error.

## Indexes

Every column that a page looks rows up by needs a btree index. The migration `20261031200000_lookup_indexes` added the ones that the plans showed were missing:

- `source_icpsr_idx`, a partial index of the sources whose license mentions ICPSR. The withdrawn-license filter reads it in every result-set query.
- `body_polity_idx`, `office_polity_idx`, `office_body_idx`, `tenure_body_idx`, and `polity_parent_parent_idx`, which polity and body pages use.
- `contest_option_alliance_idx`, a partial index on `(alliance_id, party_id)` for the 1% of options that belong to an alliance. Counting an alliance's wins had read every option of each member party, which took up to 400 ms. It now takes under a millisecond. It is added in migration `20261031230000_alliance_option_index`.

To find another missing index, run the benchmark and then look at `seq_scan` and `seq_tup_read` in `pg_stat_user_tables`.

## Heavy geometry

Some boundaries have more than a million points, Nunavut's among them. Intersecting two such shapes takes seconds. `ea coarse` keeps a simplified copy of every area geometry with more than 20,000 points in `display.coarse`. The tolerance is 0.0002 times the square root of the shape's area. A copy is kept only when it has fewer than half the points and its area is within 0.5% of the original; otherwise the row holds no geometry, and queries fall back to the full shape. `ea tiles` refreshes the table, and rows are dropped when their source geometry changes.

The `coarse()` helper in `archive.ts` returns the simplified copy when one exists. Use it only where a share is measured against the heavy shape itself or against the larger of two shapes, such as overlap with a predecessor district. Don't use it where a share is measured against the smaller shape: simplifying a large neighbor can move a small district's share by much more than 0.5%. Filters such as `&&` and `ST_Intersects` keep using the full geometry.

Across the 70 predecessor pairs of the 12 heaviest districts of Canada's 2025 election, the largest difference between coarse and exact shares was 0.00047. None changed at two decimal places, and none crossed the 1% cutoff for listing a predecessor.

## Rendering and payloads

The server's CPU time matters as much as the database's once the queries are fast. These patterns came out of CPU profiles of cold page loads.

- **Reuse collators and formatters.** `localeCompare` with an options object builds a new ICU collator on every call, which made sorting France's 35,000 communes take 3 seconds. Sort with the shared `natural` comparator in `apps/web/src/lib/format.ts`, which wraps one `Intl.Collator` with numeric ordering. Build number and date formatters with `numbers()` and `dates()` from the same file, which keep one formatter per locale and set of options. Building an `Intl.NumberFormat` takes about 16 µs and an `Intl.DateTimeFormat` about 60 µs, while reusing one takes half a microsecond.
- **Group rows once instead of filtering per row.** When a loop over areas needs each area's result sets, group them with `Map.groupBy` before the loop instead of calling `filter` inside it. Key nested sums by result set, so each set reads only its own entries. On the 2024 UK general election page, the per-area filters took 480 ms of CPU.
- **Send only what the page shows.** A polity page sends the first 20 places of each kind and the 10 largest municipalities, plus the count of each kind. When someone filters the list or asks for every place, the page loads the full list from `polities.get`. The page for France went from 4 MB of HTML to 92 KB.
- **Pack sparse arrays.** A results map is a matrix with one row per place and one column per party or independent candidate, so most cells are zero or empty. The `transport` hook in `apps/web/src/hooks.ts` encodes every array of 64 or more items where at most a quarter of the items differ from 0 or `null` as its length and the items that differ. It encodes ascending runs of integers, such as the list of columns a place lacks, as start and end pairs. The browser decodes both back to the same arrays, so components never see the encoding. The 2024 UK general election page went from 5.4 MB of HTML to 1.6 MB, or 209 kB compressed, and the 2024 US general election page went from 1.6 MB to 1.1 MB.
- **Send long lists of rows as columns.** Most of a results page's data is lists of same-shaped objects, such as one row per place with the same fields on every row. The `transport` hook also encodes every array of 64 or more plain objects whose rows all have the same keys in the same order, and it stores one list per key. When a list holds only strings, numbers, booleans, `null`, and short arrays of those, the hook sends it as a single JSON string, which the browser reads with `JSON.parse`. Other lists, and arrays of 64 or more items inside them, go through the encoder as usual, so sparse arrays are still packed. The hook skips an array in which the same row appears twice. It also does not send a list as a JSON string when a value is `undefined` or `-0`, or when the same array appears in more than one row. The decoded data then matches the original down to key order and shared objects. The one exception is a row that the page data also holds somewhere else, which would come back as a separate copy. To check, each of 60 pages was serialized again from its decoded data and compared with the original, and none differed; the rendered markup did not change either. Page data for a round of the 2025 New York City mayoral primary by election district went from 2.1 MB to 0.98 MB, and from 371 kB to 162 kB compressed. Its HTML went from 2.0 MB to 1.3 MB.
- **Look up only nearby colors when separating party colors.** `separate` in `archive.ts` gives every party or candidate a color far enough from the colors already placed. Each candidate color used to be measured against every placed color, so an election with 4,000 candidates took 4 seconds. Placed colors now sit in a grid of cells 0.125 wide, larger than the 0.1 distance that counts as far enough, so any color closer than 0.1 is in one of the 27 cells around the candidate. The search stops at the first placed color that is too close to the candidate, or at a distance of zero. The output is identical to the full scan, and the 4,000-candidate case now takes 40 to 300 ms. Each area's list of options is built from the options that got votes there plus the declared ones, instead of filtering every option in the contest for every area.
- **Nest rows with one lookup.** The places list puts each place under the place that contains it. It used to search the whole sorted list for each parent's children, which took 139 ms of main-thread time each time someone switched rounds on the New York City mayoral primary by election district, with about 4,000 places. It now groups the children by parent once with `Map.groupBy`. Together with hover preloading, a switch between rounds went from about one second to about 200 ms from click to painted frame.
- **Keep `:has()` off ancestor elements in global CSS.** In Chrome, a single rule anywhere in the page's stylesheets that tests `:has()` on an ancestor, such as Tailwind's `group-has-*` variants (`:is(:where(.group):has(...) *)`) or `:not(.a:has(.b) *)`, makes every DOM change recheck the styles of the whole document, even when no element on the page matches the rule. Switching rounds on the 2025 New York City mayoral primary recalculated the styles of about 1,600 elements each time. A `:has()` that tests the element the rule styles, such as `has-[>svg]:p-0`, doesn't cause this. The UI components now use a sibling selector (`[[data-slot=command-shortcut]~&]:hidden`) where they need one, and drop the variants that set nothing new. The rules that hide everything but the figure on an embed page moved to `apps/web/src/lib/embed.css`, which the root layout links only when the URL has an `embed` parameter. Style recalculation for each switch between rounds went from about 14 ms to 5 ms on the New York City page by election district and from 38 ms to 13 ms on the 2024 Carlow–Kilkenny count on a phone-width screen, where painting also went from about 110 ms to 78 ms. Those savings match deleting every `:has()` rule from the page. Moving between the 2025 and 2021 primaries also got faster, from about 55 ms of style work to 40 ms. Before adding a `group-has-*` or `in-*` variant with `:has()`, or an ancestor `:has()` in `app.css`, look for a sibling selector or a data attribute that the component can set itself.
- **Skip MapLibre's style validation outside development.** `Map.addLayer` and `Map.addSource` check each new layer or source against the style specification, and to do that MapLibre copies the whole style, with every layer and expression, on every call. The `validateStyle` option of the `Map` constructor doesn't reach these calls. The maps add their fill, hatch, and outline layers again on each round switch, so on the 2024 Carlow–Kilkenny count these copies took 123 ms of the 136 ms spent adding layers. The map engine in `apps/web/src/lib/map/engine.svelte.ts` now adds layers and sources through `map.style` with `validate` set to SvelteKit's `dev` flag, then calls `map._update(true)`, which is what `Map.addLayer` does after adding a layer. `setFilter` gets the same option. The dev server still validates, so a malformed layer still logs an error there. JavaScript time for each round switch went from 214 ms to 110 ms on Carlow–Kilkenny on a phone-width screen and from 148 ms to 124 ms on the New York City primary by election district. The maps draw the same thing as before, and eight map views logged no console errors or warnings.
- **Redraw the basemap only when what it draws changes.** Each round switch hands the map a new contest object, and the map used to fetch the contest's outline again and call `basemap()` with it. `basemap()` used to drop the basemap group and add it back: every land, boundary, and label layer, plus the two basemap tile sources, which made MapLibre reload and reparse the basemap tiles in its workers. `apps/web/src/lib/map/basemap.ts` now stores, for each map engine, the scheme, detail setting, outline, and inset setting it last drew, and returns early when they are the same and the basemap's land layer is still on the map. A theme change doesn't need a redraw, because the engine already sets the paint of every layer again when the theme changes. Measured back to back with the same script, JavaScript time for each round switch went from 92 ms to 58 ms on the 2025 New York City primary by election district and from 74 ms to 37 ms on the 2024 Carlow–Kilkenny count at phone width. Fifteen screenshots of map canvases, including a round switch followed by a switch to dark mode, matched the previous build pixel for pixel, apart from two pixels at the edge of one canvas that were one or two color levels off.
- **Change only the feature states that differ.** The contest map colors each place by setting a feature state on it. `paint` in `apps/web/src/lib/map/engine.svelte.ts` used to clear every feature state of the source and set them all again, so MapLibre rebuilt the paint arrays of every place in every loaded tile on each round switch. It now compares the new states with the ones it painted last. It removes the states of places that are gone, skips places whose state matches key for key, and clears a place's state before setting it only when a key was dropped. A theme change still repaints every place, because it goes through the merged path, which sets every state again. `points` also keeps the JSON of the points it last sent for each source and skips `setData` when it hasn't changed, so the dots and arrows layers no longer go back to MapLibre's worker on every switch. Over 12 switches each on a busy test machine, the median JavaScript time for a round switch went from 107 ms to 40 ms on the New York City primary by election district and from 45 ms to 32 ms on Carlow–Kilkenny at phone width. Time in `setFeatureState` went from 8.5 ms to 0.1 ms per switch, and time in MapLibre's render from 21 ms to 2.4 ms. The 15 map screenshots from the basemap change matched again pixel for pixel. Switching back to the first round, in light or dark mode, drew the same colors as loading that round fresh.
- **Read each reactive value once per derived.** Each read of a `$derived` or `$state` value runs a dependency check, so reading one inside a loop or a sort comparator adds up. The `filtered` derived in `apps/web/src/routes/[...path]/places.svelte` read the sort column, the sort direction, the filter, the list of swings, and the shared parts of place names once per row, and it read the column and direction again on every comparison. On the 2025 New York City mayoral primary by election district, with about 4,000 places, that came to tens of thousands of reads per round switch. The derived now copies each value into a local constant at its top. A benchmark ran the old and new derived with Svelte's runtime on that page's data. Recomputing the list after a round switch went from 3.0 ms to 2.0 ms, after a sort from 1.3 ms to 1.1 ms, and after a search from 2.4 ms to 1.4 ms. Both versions returned the same rows for 20 combinations of sort and search. The search also folds accents out of place names only when there is a search, which on its own took the round switch from 3.4 ms to 3.0 ms.
- **Pick the top few rows without sorting them all.** The key places panel on a contest page shows the three closest places, the three largest, and the strongest place for each of the two leading candidates. It used to sort every place once for each list and keep the first few. `best()` in `apps/web/src/routes/[...path]/contest.svelte` now walks the places once and keeps a short sorted list, and the median vote count comes from sorting a `Float64Array`. Tied places come out in the same order as with the stable sort, and the panel picked the same places on the New York City page. With its 4,036 places, building the panel went from 2.7 ms to 0.5 ms per round switch.
- **Fetch once per contest, not once per round.** The contest map fetched the contest's outline in an effect that read the `own` prop. That prop is a new object on every round switch, so each switch sent another `contests.outline` request for the same contest. The response went into deep `$state`, and the basemap's memo key then serialized the outline through Svelte's proxies. The effect now reads the contest's id and tile set through two `$derived` values, which change only when the contest does, and stores the outline with `$state.raw`. The list of outlying places now computes map colors only when the map has outlying or pooled places (such as territories drawn in insets), so most maps compute colors once per switch instead of twice. With the change to the places list above, the median JavaScript time for a round switch over 12 switches went from about 48 ms to 30 ms on the New York City primary by election district, and from about 39 ms to 25 ms on Carlow–Kilkenny at phone width. Map screenshots matched the previous build pixel for pixel. Page text did not change on the New York City primaries, Carlow–Kilkenny, the 2024 presidential election in Pennsylvania and nationally, and Islington North, through round switches, searches, and sorts. On the first pass, the Pennsylvania page seemed to have 64 more characters after every search and sort. Those characters were the map's list of nearby states, which loads after the map's style does, so it was sometimes on the page and sometimes not when the text was read. With that list left out, the text matched the previous build after all 12 steps.
- **Let the browser skip sections that are off screen.** The count table and the places list of a contest page have `content-visibility: auto`, so the browser doesn't lay out or paint them while they are out of view, and a round switch only renders the sections someone can see. The property comes on two frames after the section mounts, through the `settle` attachment in `apps/web/src/lib/settle.ts`, which sets `data-settled`. That way the first render, and a jump to `#rounds` or `#places`, lays out the whole section as before. `contain-intrinsic-size: auto none` keeps the section's last height, so the page doesn't jump when the section scrolls into view. While a section is skipped, its `innerText` is empty and reading its layout forces a full layout, so check it with `checkVisibility({ contentVisibilityAuto: true })` or wait for the `contentvisibilityautostatechange` event. Over 12 switches in the same build, with the property on and off, the median main-thread time for a round switch went from 78.7 ms to 75.7 ms on the New York City primary by election district, and from 67.4 ms to 60.8 ms on Carlow–Kilkenny at phone width. Rendering went from 20.3 ms to 16.0 ms and from 31.9 ms to 23.1 ms.
- **Read layout after the frame, not while Svelte updates the page.** The count strip and the count table scroll to keep the current round in view. They used to read `offsetLeft` and `clientWidth` while Svelte was applying the round switch, which forced a full layout in the middle of the update. SvelteKit then reads the scroll position when the navigation finishes, which forced a second one. The shared `reveal` attachment in `settle.ts` now reads the layout in a `requestAnimationFrame` callback. When the table is skipped because it is off screen, it waits for the table to come into view and scrolls it then. This removed 2.8 ms of `checkVisibility` and 0.5 ms of `offsetLeft` from each switch, and the traces show no forced layout left on the New York City page or on Carlow–Kilkenny at either width. The strip and the table scroll to the same place as before.
- **Cache the narrow-layout check.** `isNarrowLayout()` in `apps/web/src/lib/narrow-layout.svelte.ts` tells the comboboxes, the place switcher, and the map whether to use their phone layout. It used to call `getComputedStyle` and read `clientWidth` on every call, about 10 ms per round switch at phone width on Carlow–Kilkenny. It now keeps the body's width from its `ResizeObserver` entry and the root font size from a `MutationObserver` on the root element's `style`, which is the only place the text size is set. It tells Svelte only when the answer changes. Before the observers report, it reads the layout once as before. The profile of a switch no longer shows it, and the comboboxes still open as a drawer at 390 pixels and as a popover at 1,280, switch when the window is resized, and follow a larger text size.
- **Test each map color once.** The contest map draws places whose leader has a gray color at full strength instead of shading them by margin. `fills()` in `map.svelte` used to parse the computed color for every place to find out whether it was gray. It now keeps the answer for each color during a paint.

Page text did not change through round switches, searches, and sorts on the same pages as above, at 1,280 and 390 pixels wide, and the Markdown and JSON twins matched. This time the old and new builds ran side by side on the staging server and were read at the same moment. Text recorded an hour earlier on the old build differed by 14 characters on three pages, because the data had changed in the meantime.

## Checking a change

A performance change must not change what a page says. Before each one is committed, it runs on a staging server, and the same requests go to the old build and to the new one: the places and JSON twin of a nomination hub, of a presidential general election, and of a county-level contest, plus whatever endpoints call the changed query. Each request changes the case of the letters in its ids, so it gets past every cache and runs the query again. Any difference between the old and new responses counts as a bug unless the change was meant to make it. For a query rewrite, the old and new queries also run directly against the database over a hundred or more real inputs, and their rows must match.

When comparing page text before and after a frontend change, wait until the parts that load after the page does are on the page, such as the map's list of nearby places, or leave them out of the comparison. Otherwise a difference in timing looks like a difference in content.

Procedures lowercase ids after the cache lookup, so a request with changed case still misses the cache but gets the same names and paths as the lowercase request. Before this, a polity, election, or chamber requested with an uppercase id came back with an empty name.

## Measuring

The benchmark we track requests 45 representative pages one at a time against the origin, first with every cache empty and then with both tiers warm.

| Change                                                                                      | All 45 pages, cold | Slowest contest page, cold |
| ------------------------------------------------------------------------------------------- | ------------------ | -------------------------- |
| Before                                                                                      | 98.7 s             | 34 s                       |
| JIT off, lateral result-set lookups, lookup indexes, and the turnout rewrite                | 91.4 s             | 13.7 s                     |
| zstd, the owner predicate, and the recursive-CTE rewrites                                   | 80.8 s             | 13.2 s                     |
| Coarse geometry for overlaps                                                                | 69.0 s             | 3.0 s                      |
| Geometry-first lookups, lookups for lateral rollups, and the six lookup indexes             | 61.6 s             | 2.85 s                     |
| Intersects guards, grouped district lookups, and decided-race shortcuts                     | 57.4 s             | 2.83 s                     |
| Memoized path resolution, indexable peer joins, the ballot prefilter, and streamed sections | 54.7 s             | 2.72 s                     |

With both cache tiers warm, all 45 pages take 1.9 s together, and the slowest takes 0.34 s.

Pages below the county level gain the most from memoization and streaming. A Cleveland precinct page in the 2016 Ohio Senate race took 25.1 s cold. It now sends its first byte after 2.2 s and finishes streaming after about 6 s. The next precinct in the same district sends its first byte after 0.8 s. A Canadian riding opened from the national map takes 1.8 s cold, where it took more than 20 s before.

Polity and election pages with thousands of places gained the most from the rendering changes. France's polity page took 4.2 s cold and now takes 2.1 s. The 2024 UK general election page took 3.7 s and now takes 3.3 s. With the cache warm, both take under 0.15 s.

Most of the remaining cold time goes to reading from disk, because the database is about as large as the server's memory. The two slowest queries left are geometric. One draws the home page's world map, and its output is the same for every request, so the warm-up run caches it. The other query measures how much of a heavy district its predecessor covers, which means intersecting two shapes of about 90,000 points each. Pre-simplifying the world map changed its output, and btree indexes on `area_parent (area_id)` and `election (date_from, kind)` saved less than 10% on warm queries, so neither change was made.

The origin answers a cached request in under 10 ms, but the edge adds most of the time a visitor waits. From the US east coast, a cached contest response takes about 0.15 s when the Cloudflare machine that takes the request already has an open connection to the origin in Germany, and longer when it has to open one. With little traffic, between one in ten and one in four requests open a new connection.

Opening a connection used to cost three round trips across the Atlantic instead of two. Cloudflare's TLS handshake to the origin listed the post-quantum group X25519MLKEM768 as supported but sent key shares only for X25519 and an older Kyber draft. The origin's TLS library prefers X25519MLKEM768 and does not implement the draft, so it answered every new connection with a HelloRetryRequest. Turning off Cloudflare's post-quantum setting for origin connections removed that round trip. A request on a new connection now reaches the origin about 210 ms after the first packet instead of about 310 ms, and the slow requests fell from a median of 0.47 s to 0.37 s across 468 timed requests. The hop from Cloudflare to the origin now uses X25519 alone; it can go back to post-quantum once Cloudflare sends an X25519MLKEM768 key share. A Cloudflare Tunnel was also tried, and it was slower: about half of its requests took 0.3 s, for a mean of 0.23 s against 0.16 s for a direct connection.
