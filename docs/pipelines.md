# Data pipelines

This guide explains how the data pipelines in `pipelines/` load election results into the archive, and how to add a source. Read it in about fifteen minutes. The commands assume a checkout of this repository, Python 3.14 or later, and `uv`. Run every command from the `pipelines/` folder with `uv run ea`.

For the database schema and vocabulary, read [data-model.md](data-model.md). For the overall system, read [architecture.md](architecture.md).

## What a pipeline is

A pipeline turns one official source into facts the archive can publish. Each source is a Python module named by its registry name, `{iso}.{publisher}`. The name has two parts: the ISO code of the polity, such as `us`, `tr`, or `ch`, and the publisher, such as `medsl` or `bfs`. The module lives at `pipelines/ea/sources/{iso}/{publisher}.py` and defines `fetch()`, `parse()`, and `emit()`. The CLI imports `ea.sources.{name}` and calls the function named after the step.

- **Fetch** downloads the source files into the raw cache.
- **Parse** reads the raw files and writes what the pipeline will load: its packages, or, for an older pipeline, typed Parquet tables under `data/parsed/{source}/`.
- **Emit** writes to the archive. A package pipeline loads its packages, and an older pipeline builds a changeset for `apply`.

Pipelines never write to the core tables directly. Every write is recorded as a changeset, so each row has a pipeline and a source, each write is checked before it lands, and each one can be replaced or reverted later. There are two ways to write.

**Packages** are the path for every new source. A pipeline builds one package per election, plus a `geo` package for its places and a `registry` package for its parties, bodies, and offices. Each package is a folder of Parquet files, one per table, with a `package.json` manifest. It is checked without a database and then loaded in bulk, and the load records a published changeset for it. The Czech module, `cz.volby`, is the reference pattern. See [Packages](#packages).

**Changesets** carry everything else: the pipelines written before packages existed, curated records such as the list of countries, entity matching and merges, corrections, and live results. Canada's federal elections module, `ca.elections`, is the reference pattern. A changeset is a folder with a `manifest.json` file and one Parquet file per target table. The manifest records the author, the pipeline name and version, the kind of change, the declared scope, the order in which the tables publish, and the git commit, branch, and checkout path that ran the emit. Each apply and publish appends a line to `data/logs/provenance.tsv` with the time, the step, the changeset, its status, and the commit, branch, and checkout path it ran from. `ea emit` refuses an import changeset from a pipeline that has no changeset from before November 15, 2026, when packages became the path for new sources. A development database that holds no changesets from before that date is exempt, so a fresh checkout can still load the older pipelines.

`apply` loads a changeset into a staging schema, runs every applicable check, and computes the difference from the current data. It then publishes the changeset in one transaction. A changeset publishes automatically when every check passes, if it comes from an official body and every source is a registered official source. Any other changeset is set to `pending_review`, including every changeset from a person or an agent. A reviewer then publishes it with `ea publish`, or reverts it with `ea revert`.

## Packages

A package's key is `{pipeline}/{name}`, such as `cz.volby/ps-2021`, and `p.write()` puts it in `data/packages/{key}/build/`. Its manifest records the pipeline, a summary, the packages it depends on, the ids it references outside itself (`external`), the git commit that built it, the raw files it cites, the check findings it accepts and why, a row count for each table, and a digest of its table data.

- **Ids** come from `p.id(kind, *parts)`, a UUIDv5 of the pipeline, the kind, and the source's own key, so a rebuild gives the same ids and parsing never needs the database. A row that points outside the package and its dependencies lists that id in `p.external`. Countries are referenced this way, by `uuid5(NAMESPACE, "polity\x1f{ISO}")`. A package can create a region, county, or other sub-national polity with `polity`, `polity_parent`, and `polity_territory` rows, keyed as `uuid5(NAMESPACE, "polity\x1f{ISO 3166-2 code}")` where the polity has one, so a later pipeline derives the same id; `ar.provinces` is the example. A package cannot create a country, so a country the archive lacks is first added to the curated `world.countries` changeset.
- **Counts** in `result_value` and `declared` are exact. A pipeline passes each value as an `int`, a `Decimal`, or a decimal string; a float is read through its shortest form, so `0.1` stays `0.1`. A table whose values are all whole numbers is written as Int64. When any value has a fraction, as with Japan's proportionally split ambiguous ballots or surplus transfers in a single transferable vote count, the whole table is written as a decimal with the fewest places that hold every value exactly, up to 9 places. A value that needs more places stops the build, so round it to the precision the source publishes. When loading, the value is stored without trailing zeros, and `ea package export` carries fractional values from the changeset path the same way.
- **Flows** are `result_flow` rows, for votes that moved from one option to another, such as the transfers in a single transferable vote count. A row has the same columns as a `result_value` row plus `from_option_id`: `result_set_id`, `unit_id`, `from_option_id`, `option_id`, `channel`, `measure`, `count_round`, `flags`, and `value`. Add them with `p.add("result_flow", ...)` or `p.frame("result_flow", ...)`. The row says that `value` votes went from `from_option_id` to `option_id` in that count round. Leave `from_option_id` empty for votes that enter an option from outside any option, such as a surplus that no one holds. The load stores an empty option as key 0, as it does for `result_value`. Values are exact like counts, so a fractional transfer needs no rounding. Flows are a fact table like `result_value`: loading a new version replaces the flows of the result sets the package's earlier versions wrote, a package without a `result_flow` file withdraws them, and the load verifies each result set's flow rows and sum against the package. They do not enter rollups.
- **`ea package check`** runs in DuckDB, with no database. It checks that keys are unique (`unique.fact` for values, `unique.flow` for flows), that every reference resolves inside the package, its dependencies, or its external ids, that electoral rules match the engine's schema, and that the accounting and outcome checks hold. Flows also fail `fact.flow_negative` (a negative value), `fact.flow_self` (an option that transfers to itself), and `fact.flow_option_contest` (an option from another contest than the result set's). A finding blocks the load unless the pipeline accepts its code with `p.accept(code, reason)`, and the reason is stored with the load.
- **`ea package ready`** asks the database what `check` cannot see: that every external id exists in the database or is minted by another package in the same batch, that every dependency is loaded or in the same batch, that every required column without a default has a value, that every enum column holds only values the database allows, that every column exists (for `result_flow`, only when the database or snapshot lists it), and, against the database, that no outline overlaps the validity of an outline another package already loaded for the same area, counting the outlines of the changesets a package adopts as its own (`ready.area_geometry`; `ea package check` reports the same overlap within a package and its dependencies as `unique.area_geometry`). It also fails when two packages of the batch, or one package under two ids, declare a reporting unit with the same scheme and code for overlapping validity (`ready.unit_twice`), since the database holds one such unit at a time; `ea package check` reports the same repeat within one package as `unique.unit_code`. Emit each unit from one package and list it as external in the others. It also fails when an external id (scheme and value) is held under another pipeline's changeset or added by two packages of the batch (`ready.external_id`), when an entity would get a second current slug or a slug path is held for another entity (`ready.slug`), and when two packages of the batch add the same entity id (`ready.entity_twice`); against a snapshot, these read `external_id.parquet` and `slug.parquet` in the reference partitions downloaded beside it. It writes nothing, so run it before a load. With `--snapshot <file>`, it runs the same checks against a reference snapshot instead of the database, so you can run it on a machine without one. `ea package snapshot <file>` writes that snapshot from the database: every polity, scheme, and country-level area id, the loaded package keys, and the rules for each column. In snapshot mode, an external id is found only if it is one of those polities, schemes, or areas, or another package in the batch mints it. `ea package load` loads a batch in order. Each package comes after the packages it depends on and after every package in the batch that mints an id it references. So a runoff can cite its first round, and an election can cite the country area from the geo package, without declaring either as a dependency.
- **`ea package load`** runs the checks again and loads the batch in dependency order, committing one transaction for every 20 packages, so a large batch stays within the database's lock table. Packages that depend on each other, or that use an id another package of the batch mints, always share one transaction, even past 20, so a dependency in the batch counts as loaded. In that transaction every package writes its rows first, and the deletes a foreign key blocks (a geo package's dropped areas that contests and reporting units still point at) run after the last package has re-pointed them, dependents first. A row that a new package declares identically to one an older package of the same polity wrote moves to the new package, so the older package's next version doesn't delete it. A run with any package that fails its checks loads nothing. Each package records a published changeset of kind `import`, whose scope names the package, its version, and its digest. A package whose digest matches its last load is skipped, unless rows it wrote still reference a merged entity. Loading a batch again after a failure picks up where the failed transaction began. A new version replaces the rows that the package's earlier versions wrote. A package built before a merge still carries the duplicate's id, so the load points every reference to a merged entity at its survivor, as publish does, and a duplicate's name or slug comes in as a redirect rather than the preferred name or current slug. The load refuses to commit a package whose rows still reference a merged entity. An empty required column with a fixed default, such as a date's precision, takes the default. Before each commit, the load compares the rows, values, and seats in the database with the packages in that transaction, and rolls back on any difference. It keeps a copy of each loaded version in `data/packages/{key}/v{n}/`, so that `{key}@v{n}` can reload it.
- **Columns added later.** A column added to the format after packages were already built (so far only `candidacy.preference_option_id`) is left out of the Parquet file when no row fills it. Earlier packages and their digests stay valid, every reader takes a missing column as null, and `ready` reports such a column only when a package fills it before the database has it.
- **Tables added later.** `body_size` (a body's seats over a validity range) and `ballot_question_text` (a question's wording, keyed by its id) joined the format after packages were already built, so a pipeline moved off the changeset path keeps its seat counts and question texts. A digest covers only the tables a package holds, so earlier packages and their digests stay valid.
- **Preference votes** within a list are written as the [data model](data-model.md#preference-votes-within-a-list) describes: a `candidate` option under the list option with its measure-7 values, and `preference_option_id` on the candidacy. `ea package check` refuses a candidacy that names an option that isn't a `candidate` option under its own list in the same contest (`fact.preference_option`), two candidacies that name the same option (`unique.preference_option`), and any measure other than 7 on an option a candidacy names (`fact.preference_measure`). `accounting.preference_over_list` reports a candidate whose preference votes in a unit exceed the list's votes there times the candidacy's `ballot_lines`. A package may accept it only where the source's figures cause it, as with panachage, where voters for other lists can mark the candidate too.
- **`ea package export <pipeline>`** turns the published rows of a changeset-path pipeline into the package `{pipeline}/all`, ids included. Loading that package adopts the old changesets and rewrites nothing.

## The raw cache

The raw cache keeps every downloaded file exactly as the source served it. Files live under `data/raw/{source}/`. Each file is named by its SHA-256 hash and keeps the extension it arrived with, so `data/raw/{source}/{sha256}.{ext}`. Each source folder also has an `index.json` file. The index records, for each file, the URL it came from, its SHA-256 hash, its retrieval time, and its media type.

Three rules govern the cache:

- Downloads are never edited. Parsing reads the cached file and writes its output elsewhere.
- A re-run reuses the cached file when the index already has it. A run therefore reproduces the same parse and the same changeset from the cache alone, even after the source changes or goes offline.
- Raw files are untrusted input. They are read as data, never run as code.

Some sources need a different shape of request. A query API that requires a POST passes a `body=` argument to `raw.fetch` and `raw.cached`. The index keys such an entry by the URL plus a hash of the JSON body, and it stores the body, so each query becomes its own artifact. A source that a person crawls and supplies, rather than a URL the pipeline can fetch, goes into the cache through `raw.store`. Wikipedia pages are pinned to the revision current at retrieval time, so a lost file can be fetched again exactly.

Files that a person downloads by hand live in `data/inbox/manual/MF-###/`, one numbered folder per download request, because the site blocks scripted downloads; the pipeline that needs them reads them from there and adds them to the cache with `raw.store`.

`emit` turns the index entries it used into `source_artifact` rows in the changeset. Those rows let any published fact trace back to the file it came from.

The `ea raw` command maintains the cache:

- `uv run ea raw verify [source] [--quick]` checks each entry's file, size, and hash against the index. It reports unindexed files and exits nonzero when a file is missing or changed. `--quick` checks sizes without hashing.
- `uv run ea raw license [source]` records the licenses of the sources that cite each entry. Those licenses determine whether the raw file may be shared.
- `uv run ea raw pin [source]` pins Wikipedia fetches that were cached before pinning existed.
- `uv run ea raw retire [source]` moves unindexed files older than a day to `data/retired/raw/{source}/`.

## Commands

The main steps take a registry name, except `apply`, `publish`, and `revert`, which take a changeset. Run `uv run ea <command> --help` for each command's arguments.

- `uv run ea fetch <source>` downloads the source's files into the raw cache.
- `uv run ea parse <source>` writes typed Parquet tables under `data/parsed/<source>/`. It fails when the rows disagree with the totals the source prints.
- `uv run ea emit <source>` writes a changeset folder and prints its path.
- `uv run ea emit census.<cc>` writes a changeset from the country's census file, `pipelines/ea/census/<cc>.json`. The file lists the sources, the tiers of government, and each class of election with its selectors (the contest kinds, offices, and schemes that map held contests to the class), its dates, and its contest and seat counts. A date row with `through` and no `contests` is a span whose elections are not yet counted. A `states` entry on a date row becomes a census date for that member state, with its constituency count and source. A re-emit deletes the census rows the file no longer holds, so remove a row from the file only when you mean to delete it from the archive.
- `uv run ea emit census.world` writes the census world tier from `pipelines/ea/census/world.json`. It has one row per ISO 3166-1 code, plus Kosovo, and each row is `own`, `within` another polity, or `none`. Each row gives the CLDR English name and the source that settles the polity's status. The tier also lists polities without an ISO 3166-1 code: de facto states (`de_facto`, coded under their UN-recognized parent, such as `CY-NC`, with that parent in `recognized_within`) and former states (`former`, under their ISO 3166-3 alpha-3 code, such as `SUN`, or an `X`-prefixed code where none exists). `uv run ea census world` writes `.agents/spec/coverage/world-census.md` from it, with each `own` country's census state (none, in progress, or published) and the elections the archive holds.
- `uv run ea apply <changeset-folder>` loads a changeset, runs its checks, and publishes it or sets it to `pending_review`.
- `uv run ea publish <changeset-id> [--reviewer <user-id>]` publishes a changeset that is in `pending_review`.
- `uv run ea revert <changeset-id> "<reason>" [--reviewer <user-id>]` rejects an unpublished changeset, or undoes a published one that no later changeset builds on.
- `uv run ea package {check,ready,load} <key>...` checks, readies, or loads packages by key (`{pipeline}/{name}`). `uv run ea package ready <key>... --snapshot <file>` readies them against a reference snapshot, which `uv run ea package snapshot <file>` writes. `uv run ea package export <pipeline>...` exports a changeset-path pipeline as a package. [Packages](#packages) describes each one.
- `uv run ea raw {verify,license,pin,retire}` maintains the raw cache, as described above.
- `uv run ea fixtures` exports the engine's golden-test fixtures from the database.
- `uv run ea rollup <set>...` recomputes the area rollups of the named result sets. `--affected` rebuilds every set whose rollups are missing at its district. `--scope <sets>` lists the places with at least that many rolled-up result sets in `area_day_scope` and rebuilds their rows in `area_day_set`.
- `uv run ea covers` fills the `contest_cover` and `contest_top` tables that contest pages read. For each table, it stores a row for every contest that has none, then compares a sample of up to 5,000 stored rows with the live query, and logs and deletes any row that differs. A publish, a revert, and `ea rollup` each delete the rows of the contests they could have changed, so run it after a batch of publishes.
- `uv run ea crowns` refreshes the `election_crown` table: one row per child election of an election with at least 40 children that have a current slug. With no argument it rebuilds only the children that changed since its last run, plus any child that has no row, and records the newest publish it has seen in `election_crown_mark`. `ea crowns <path>` rebuilds every child of one election, or of every such election of a polity, and `--all` rebuilds them all. Neither form moves the mark.
- `uv run ea coverage` measures a polity's coverage against its official goals and writes the report, with subcommands for the United States (`us`), each polity with a published census, and the coverage tables the app reads (`refresh` and `rebuild`, which first rebuild `contest_class`).
- `uv run ea tiles [scheme]` builds one PMTiles archive per boundary set, with geometry only.
- `uv run ea hexes` builds the maps of hex tiles that the app serves from `apps/web/src/lib/server/hex/`, placing each election's districts inside the grids in `pipelines/ea/hexgrid/`.
- `uv run ea cartograms` rebuilds the cartogram and tile map of every US House election since 1788, every UK general election since 1832, every French legislative election since 2012, and every Turkish general election since 1923 from the district and province shapes, then runs `ea hexes`. It takes several hours.
- `uv run ea rasters [scheme]` builds a raster archive of area IDs for each boundary set of 1,000 or more areas.
- `uv run ea basemap {br,ca,ch,de,fr,gb,ie,it,tr,us}` builds a polity's planar basemap. You can list several schemes in one command.
- `uv run ea basemap de tr --historical 261111` builds only the period layers from OpenHistoricalMap's daily planet of that date (YYMMDD). It leaves the Protomaps basemap alone. The planet goes to the raw cache as `world.ohm`. The command streams it with pyosmium and an on-disk node index, so memory stays small. For each scheme it writes `data/plane/world.basemap/{scheme}.historical.pmtiles` with two layers: `rail` (railways) and `borders` (German boundaries valid in 1950 or 1980, plus the Türkiye, Hatay State, and République syrienne outlines, clipped to land). Rail covers the whole frame the basemap draws, and a rail feature with `out=1` lies outside the polity's land.
  - Every feature has `start_date` and `end_date` plus the day numbers `s` and `e` (days since 1970-01-01). A feature is valid on day D when `s <= D < e`, and a missing `e` means the feature is still open. A year or year-month end covers that whole period, so `end_date` is the first day after it. We drop features with no `start_date`, with a start after 2026, with an unparseable date, or with an end that is not after its start.
  - We keep CC0, public domain, CC BY (credited), and untagged features, which we treat as CC0 by default. We drop ODbL, CC BY-SA, GPL, and unclassified licenses.
  - The command also writes `{scheme}.historical.credits.json`, which lists the credit text for each CC BY source with feature counts per theme and license class, and `historical.json`, which holds the day format, the rejected license values, and a muted mode that hides modern roads, streets, and labels for elections before 1970.
- `uv run ea search` rebuilds the whole search index from names and slugs and recomputes every entity's rank. Publishing a changeset already refreshes the search documents of the entities it adds, renames, merges, unmerges, or retires, so run this command when ranks need updating, for example after a large import changes how many candidacies people have.
- `uv run --with pyicu==2.17 ea names latin` adds Latin-script names to every entity that has none, and sentence-case forms of names the source prints in all capitals. It never removes a name. It changes a source's own names only through those sentence-case forms. Once an all-caps name has one, the pass marks the all-caps row as kind `ballot` and no longer preferred, so each language keeps one preferred native name while the source's text stays as printed. People and places are transliterated with each language's official romanization through ICU and CLDR transforms (Revised Romanization for Korean, ELOT 743 for Greek, Bulgaria's 2009 system, Ukraine's 2010 system, MNS 5217 for Mongolian, and BGN/PCGN where a language has no official system). Parties, alliances, bodies, offices, and contests get an English translation. Names that a script cannot carry over without loss wait in a queue on the Storage Box (`names/queue.json`) for the model step, and so do all translations. Those names are Korean, Japanese, and Taiwanese personal names, Japanese place names in kanji, and Arabic, Hebrew, and South Asian names. Each run emits one changeset per language under the pipeline `names.latin`, with kind `transliteration`, `english`, or `official`, script `Latn` for the Latin forms, and the archive's own source, then one changeset that marks the all-caps rows. It applies and publishes a changeset only when its checks find nothing and it either adds names alone or only marks all-caps rows as `ballot`; a publish that turns out to change anything else is reverted. The first run scans the whole archive; later runs read only the entities that changesets published since the last run touched, plus the ones still waiting for the model. The loader runs it after every load. PyICU builds against the system ICU, so it is not a project dependency: on the Mac set `PKG_CONFIG_PATH` to Homebrew's `icu4c`, and on ea-fsn2 a prebuilt wheel lives in `~/.local/share/ea-wheels` (`UV_FIND_LINKS`).
- `anthropic-batch uv run ea names model` runs on ea-fsn2 every 30 minutes from `ea-names-model.timer`, after any naming pass in progress has finished. It sends the queued names to Haiku 5.5 through the Message Batches API, sends every draft to a second review batch, and writes the reviewed answers to `names/answers.json` on the Storage Box, where the next `ea names latin` run picks them up. Each submission stops if it would cost more than $40. Only one machine may run it, because the record of batch spending (`data/batch/`) and its drafts (`data/names/drafts.json`) are local files; they moved from the Mac to ea-fsn2 on 2026-11-19. `uv run ea names quote` estimates the cost of the queue.
- `uv run ea release [--calver <label>]` writes the bulk export to `data/releases/<label>/`. The label defaults to today's UTC date. The export has three licensed bundles, CC BY 4.0, CC BY-SA 4.0, and ODbL 1.0, and each bundle holds the facts that its sources allow. Result values come as Parquet and gzipped CSV, split by polity and decade (US results split by state). Shapes come as GeoParquet, split by boundary scheme and vintage. Each entity table is one file in Parquet and gzipped CSV. The command holds back anything restricted, non-commercial, or revocable, everything from THEA, and any shape without a license. Each release folder has an `ATTRIBUTION.md`, a `manifest.json`, and a `SHA256SUMS` file. No file is larger than 2 GiB, and a release holds at most 1,000 files. The command writes files only; it does not upload anything.
- `uv run ea scans {prepare,run,status,emit,layout,statewide} [name]` drives the batch vision pipeline for scanned tables. See the digitization section below.

## Worked example: Canadian federal elections

This example loads Canada's federal results into a development database. It runs against your own database, not the archive's production data. Set `DATABASE_URL` in a `.env` file at the repository root, and copy `.env.example` as a starting point. The database needs PostgreSQL with PostGIS and the migrations applied. The README describes the migration command.

```sh
cd pipelines
uv run ea fetch ca.elections
uv run ea parse ca.elections
uv run ea apply "$(uv run ea emit ca.elections)"
```

`fetch` downloads the poll-level result files, the riding boundaries, and the by-election results. A second run reuses every cached file that the index already lists.

`parse` reads the cached files and writes Parquet tables under `data/parsed/ca.elections/`. If the parsed rows disagree with the totals the source prints, the parse fails, so a bad parse never reaches the changeset.

`emit` builds the changeset and prints the folder path. The shell passes that path to `apply`, which loads the changeset, checks it, and publishes it. Because Canada's federal results come from an official body, the changeset publishes automatically when every check passes.

## Checks

A changeset must pass its checks before it publishes. Each check has a stable code. A finding that names an entity or a result set becomes a `flag` row, which the public site shows. The changeset's `checks` field keeps the summary: the diff, the counts per code, and sample rows.

These are the checks in the current code:

- **Accounting** (`accounting.ballots_sum`, `accounting.votes_valid`, `accounting.turnout`) checks that valid, invalid, and blank ballots add up to the ballots cast, that option votes sum to the valid total in single-member contests, and that turnout does not exceed the number registered.
- **Outcomes** (`outcomes.winner`, `outcomes.list_members`) checks that a declared winner has the most votes in single-member contests, and that a list declares no more elected members than its seats. Instant-runoff contests are exempt from the winner check, because the first-round leader can lose.
- **Reference** (`reference.facts`, `reference.stranded`) checks that every unit, area, and option resolves, and that a published result set does not hold facts that point at a deleted row.
- **Immutability** (`facts.immutable`) refuses facts for a published result set that another pipeline last wrote.
- **Rules** (`rules.schema`) checks that each electoral system's rules validate against the engine's JSON schema.
- **Geometry** (`geometry.valid`) checks that polygons are valid.
- **Elections** (`election.empty`, a warning) flags a new held election that has no contests and no child elections, such as a year whose parse went missing before the emit.
- **Scope** (`scope.polity`, `scope.owner`, `scope.overlap`) checks that the diff touches only what the manifest declares, and that a pipeline never changes a row that another pipeline or a person last wrote. `scope.overlap` names each staged temporal row whose period overlaps a different row another pipeline published, and `ea publish` refuses such a changeset before running the other checks, because the insert would break the period key.

Apply and publish print each check's code and running time to stderr. Each check runs under a 20-minute statement timeout. A check that exceeds it fails the apply with an error naming the check and the changeset, so a pathological query never holds a transaction open for hours. A check reaches the public tables only through the ids that the changeset stages, so its cost grows with the changeset rather than the archive.

Some checks run at apply time, and some run in the engine's golden tests. The engine recomputes seat allocations from the rules and compares them with the official seats. Declared seats are stored as published, and the engine's output is compared against them, never written over them.

## Re-emits and result sets

A re-emit runs the same pipeline again and writes a new changeset. Re-emits must be safe, so the archive holds several rules about IDs and rows.

**IDs are stable.** The emit resolves each entity by its natural key: the polity's ISO code, the area code within a scheme, the unit code within a scheme, or the source's publisher and title. Where a scheme reuses codes, the emit resolves them on a date, as Canada's riding numbers do. Pipeline-specific keys live in `external_id` under a `{source}.{kind}` scheme. An entity that no key resolves gets a UUIDv5 derived from its scheme and key, so a re-emit into a rebuilt database mints the same IDs again.

**Re-emits replace their own rows.** A changeset that stages facts for a result set its own pipeline last wrote replaces that set's facts. A fix to the parse, the mapping, or a key is therefore a re-emit into the same set. Temporal rows that a staged row overlaps are replaced, and keyed child rows that the pipeline no longer stages are deleted. Rows another pipeline wrote, and entities, are never deleted this way.

**Disagreeing or finer sources supersede.** When a second source disagrees with the first, or when a source offers a finer breakdown of the same contest, the emit publishes a superseding result set. The new set becomes the default and records what it supersedes. The old set stays in the archive as superseded and non-default. A superseding set must also stage the contest's outcomes, because `apply` copies outcomes only when it flips a default.

**Published sets become immutable.** Until the archive's public launch, a re-emit can replace the facts of a set that its own pipeline last wrote. After launch, a published result set is immutable. Corrections then arrive as superseding sets.

**Reverting is the fallback.** `ea revert` undoes a changeset. It deletes the result sets the changeset created, restores the rows it changed from their history, and removes the entities it minted. A source the changeset added stays when later changesets cite it, and is handed to the earliest of them. The revert fails when a later changeset changed a row it wrote, references an entity it created, or holds facts on its units. The revert also fails when the changeset replaced facts in a set it did not create. Those corrections are fixed forward with another re-emit. Use `revert` when a re-emit cannot express the fix, such as an entity that should not exist. Revert newer changesets first, and move the reverted folders to `data/retired`.

## Withdrawal at a source's request

When a source asks the archive to remove or limit its data, the pipeline that owns the source carries it out in four steps.

1. **Mark the source.** The pipeline stages a new license text on the source, starting with `Withdrawn: <body> asked on <date> …` for a full withdrawal or `Limited: …` for a partial one. Because the mark is part of the license, it goes through a changeset like any other change.
2. **Hide what cites it.** `licensed()` hides every result set that cites a withdrawn source, so the site, the API, the MCP server, and embeds stop serving it at once. The restricted cache class keeps the source's raw files out of bulk releases.
3. **Drop the sets.** The owning pipeline then drops the result sets with `result_set_drop` and retires the entities that existed only for them. A retired entity's public ID returns HTTP 410 and the reason.
4. **Carry out limits in the emit step.** The pipeline changes what it emits, so a limit shows up in the staged rows.

`_history` keeps the deleted rows for the audit trail and is never served.

## Entity resolution

Matching people, parties, and places across elections and sources runs in three stages. Deterministic rules come first: official IDs, and exact normalized names within a polity and period. Wikidata lookups come second. AI-assisted matching comes last, and it outputs a confidence score with the evidence behind it. High-confidence matches are applied automatically as `match` changesets. Everything else goes to review. A wrong match is undone by reverting its changeset.

### Parties

The `wikidata` pipeline matches each party to a Wikidata item. It queries parties in every country the archive holds, in English and in that country's own languages, and compares names in their own script after folding case and accents. It scores each item by how well its labels, aliases, short names, and official names match the party's names, and checks the item's founding and dissolution dates against the party's elections. The top item must score well enough and beat its runner-up. A party that another pipeline has already linked keeps its link. The same pipeline imports each party's colors and political position from Wikidata. The module keeps a party's hand-curated color, or a political position that the source leaves out, as a constant with a note, so reviewers can see where it came from.

The `party_wikidata_links` package adds hand-matched Wikidata items for parties the name matcher leaves out, such as electoral committees and lists that won at least 1% of a vote without a seat. `party_wikidata_links.tsv` lists each party, the years it stood, the item, and how it was matched (its label, a former name, or the Wikipedia page Party Facts cites). The build checks each item's country and founding and dissolution dates against a Wikidata query, and it lists only items no other party holds; a party that duplicates one already holding its item needs a merge instead.

The `partyfacts` pipeline adds each party's Party Facts IDs as `external_id` rows with scheme `partyfacts`. Party Facts' data is CC0 and covers every country. The pipeline matches Party Facts' three-letter country codes to the archive's through Wikidata. A Party Facts party matches one of ours through the Wikidata item of the Wikipedia page it cites, or through its ParlGov party ID. If two routes send one Party Facts party to different parties, the pipeline skips it. A party may hold several Party Facts IDs, because Party Facts splits or merges some parties the archive keeps as one. Treat the IDs as crosswalk keys, not identities. Each match carries a citation whose locator names the route. A party that matches only through ParlGov and has no Wikidata link gets the Wikidata item of Party Facts' Wikipedia page, but only when all of its Party Facts IDs cite that one item and no other party holds it.

Every source mints its own parties, so one party often exists once for each pipeline or package that names it. The `party_merges` pipeline joins those records. It groups the live parties of one polity that share a full name (an official, English, native, ballot, historical, or transliterated name, compared after folding case and accents) and that come from at least two pipelines or packages. Some names never form a group: a name that only says its candidates are independent, a numbered list, and a name of fewer than four letters. Parties of kind `list_vehicle`, `independent_group`, `nuance`, `parliamentary_group`, or `caucus` never join a group either, because each one is a separate entity by design; Poland registers a new electoral committee for each election, for example.

A group stays apart when two of its members hold different Wikidata items, when their names in the native script differ (as with two Korean parties whose English translations coincide), when a `party_relation` links two of them (a refounding or a merger, which the data model records as a new party), or when `party_apart.tsv` lists the pair.

A group is held for review when its members' kinds differ, unless it joins parties only with blocs or federations; then it merges, and the surviving record keeps its own kind. Two members need not share a name, as long as each shares one with another member. A group is also held when one pipeline or package holds two members that ran in the same election. Two records from one source that ran in different elections merge, because the source minted the same party again for each election. A group is also held when its members cannot all be linked by place. Two members link when they share a district, or when one of them ran nationally and either of the two ran in at least three districts. A member ran nationally when it stood in a contest that the census places at the country's top tier, in a contest for the whole country, in a district named after the country, or in a European Parliament election. Every member must link to the rest through a chain of such links. A group is also held when the dates do not fit: a member that ran more than five years before the founding year of the group's Wikidata item or more than a year after its dissolution year, or, when the item has no dates, a gap of more than 12 years between records. A group is also held when its only shared name has four letters or fewer and none of its members has a Wikidata item. A group waits for the next run while a member's pipeline has a changeset waiting.

Every other group merges into the member that carries the Wikidata item, or else the one with the most elections, and then the one with the most options. Pairs reviewed by hand go in `party_same.tsv` with the evidence for each. Each emit writes `groups.tsv.gz` into the changeset folder, with every group's members, outcome, and reason.

Loads never look for an existing party: each source mints its own, and `party_merges` joins them afterward. On the production host, a timer runs every six hours. When parties have loaded since the last run, it runs `wikidata` and `partyfacts`, then `party_merges`. When people have loaded, it runs `crosswalk`. The timer applies the two merge changesets but does not publish them. The changeset grant publishes them after its usual wait, unless a run merges more than 500 parties or 5,000 people; a run that large waits for review.

### People

Two people who are the same person merge with `cs.merge(duplicate, survivor)`. Publishing the merge re-points every foreign key and every fact that references the duplicate, moves the duplicate's names and slugs to redirects, and records each re-pointed row in `fact_rekey`, so `ea revert` can undo the merge. The merge is refused when the survivor already holds a conflicting row for the same key.

When the survivor already holds a dated row for an overlapping period, a merge deletes the duplicate's row, and the table's history keeps it. The survivor's own row is the one that counts for that period, and a row left on the duplicate would let any query that selects by a value, such as a code or a parent, pick up the merged-away entity. A changeset or package written before a merge still carries the duplicate's id. Publish and `ea package load` point each such reference at the survivor, including the columns in the table's key (such as `area_geometry.area_id` or `alliance_member.party_id`). When the survivor already holds a row with the same key, or an overlapping period for a dated key, the survivor's row stays and the duplicate's row is skipped, unless the pipeline or package being loaded wrote that row itself. A row that would bring back a contest, option, candidacy, or reporting unit that a merge deleted is skipped too. Both paths then refuse to commit a row that still references a merged entity. They also refuse to retire an entity that is already merged. `uv run ea merged` lists every row that still references a merged entity. The `merged_strays` pipeline drops each such dated row when the survivor holds its own row for an overlapping period, which clears the rows that merges published before this rule left on duplicates.

A wrong merge is undone with `cs.unmerge(duplicate, reason)`, which stages an `entity_merge_drop` row. Only the pipeline that wrote the merge can undo it. Publish handles the unmerge before any other table. It moves each row that the merge re-pointed back to the duplicate, restores the duplicate's preferred name and current slug, puts back each row that the merge deleted because the survivor already had the same one or its own row for an overlapping period, and clears each column that the merge filled on the survivor from the duplicate. A row that another pipeline has rewritten since the merge stays with the survivor, and publish prints how many such rows it left. The same changeset can then merge the duplicate into the right person. Publish refuses to unmerge an election, contest, option, candidacy, or reporting unit, or any type whose facts are keyed by its `k`, because merging those deletes rows or rekeys facts that an unmerge cannot rebuild.

The `crosswalk` pipeline is the general person matcher. It runs as a batch job after loads, so loads mint people under their own source keys and never wait on it. It forms pairs only from races in France, Spain, Finland, Italy, Poland, Canada, Luxembourg, and Ireland, where the same-day namesake rate keeps wrong merges under 0.5% (ops#4178). The checks that keep two records apart still read every race each person ran, in any country. It joins two person records when nothing tells them apart and one of two rules holds. Under the seat rule, the same printed name ran for the same seat (one district of an office or body, or an office elected without districts) within 12 years. Under the body rule, the same printed name ran for the same legislature of a country, state, or region, under the same party at their nearest races, within 12 years, and no one else of that name ever ran in that country, state, or region. Names are compared after folding case and accents, dropping middle initials, and reading common nicknames such as Bill as William. Two records stay apart when they ran on the same day, when one ran for another seat within 60 days of the other's race, when their first names or middle initials disagree, when their birth dates differ, when one ran more than a year after the other's death, when they hold different identifiers in another system (such as two Wikidata items or two FEC IDs), or when either one comes from a pipeline with a changeset waiting. A group of records merges only when every pair in it passes. Pairs that need a person's judgment are listed by hand with the evidence behind them: `crosswalk_same.tsv` joins records of one person, and `crosswalk_apart.tsv` keeps apart records that the rules would join, such as a father and son who held the same seat. Each emit merges at most 200,000 records, so a large backlog publishes over several runs. Every emit writes `merges.tsv.gz` and `edges.tsv.gz` into the changeset folder, naming the rule, the shared name, the seat or body, the party, and the dates behind each merge, and the reason each refused group was held back. Brazilian and Turkish candidates are left to `br.match`, `br.tse_people`, and `tr.match`.

Older pipelines also match people with their own matchers. `us.match` joins book persons, FEC candidate IDs, and Electoral College people. `tr.match` joins members of the national assembly across consecutive elections when they share a printed name and electoral district. `ca.match` joins candidates across consecutive federal elections when they share a printed name and overlapping ridings. `ca.quebec_match` joins Quebec provincial candidates who share a printed name and run in the same or a namesake riding at the next general election, sitting members who run for the same party at the next general election, and candidates whose given names differ only by a shortened or extended form in the same or a namesake riding. `fr.match` joins heads of list in the regional elections with each other when they share a surname, a compatible forename, and a region, and with législatives, sénatoriales, départementales, and municipal heads of list who share their full name and ran in the same region. It also joins législatives, sénatoriales, and départementales candidates who share a printed name and a département across elections at most 12 years apart, holding a name back when a namesake ran in the same election, stood in another commune of the département in the same municipal election, carries another Wikidata item, or has another birth date. Two adjacent départements are joined only when they are the only places that name ever stood, and municipal heads of list join only from a single commune. `id.dpd_match` joins Indonesian Regional Representative Council (DPD) candidates of 2019 and 2024 who share a printed name without titles, degrees, or initials in the same province or in a Papuan province split from it, and gives the members elected the Wikidata item that Indonesian Wikipedia lists for their term or that holds the DPD membership. `br.match` joins Brazilian candidates of 1945 to 1990, whom the early TSE files name without an ID or birth date, with candidates of 1994 and later who share their full name in the same state. The later person must have been 21 to 75 at the earlier person's first election and be the only such namesake, and the two must also share a party or a ballot name, or have run again by 1994, or both have won; a municipal candidate must share both a party and a ballot name. It also joins the presidential and vice-presidential candidates of 1945 to 1989 with the state candidates who share their full name, and joins persons across states who share a full name that no other candidate of a plausible age bears, when their careers follow one another (each ends before the next begins) and a shared Wikidata item, or a shared party between neighboring careers at most 12 years apart, links them, unless they hold different items or birth years; it then gives winners of 1945 to 1990 the Wikidata item whose label or alias is their full or ballot name and that held the same office for the same state in that term. Each matcher keeps the person with the most evidence, such as an official ID, a Wikidata item, or the most candidacies, and merges the rest into it. A person who was never real, such as a parse artifact, is retired with an `entity_retirement` row rather than merged, and the retirement refuses if anything still references the entity.

`br.municipais` and `br.tse_history` key a candidate by name and birth date, and `br.municipais` reuses `br.tse_history`'s persons. Before either emits, `br.identity.namesakes` reads the voter titles and tax numbers that `ea parse br.tse_people` writes, groups each key's candidacies into exact-key identities, and keeps two identities apart when they carry different tax numbers or stood in the same year. The identity that stood first keeps the key, and each other one moves to the key followed by its first voter title. A title that was mistyped or reissued in a year whose roster withholds tax numbers (2024) stays with the identity it shares a place with, or with the first one. Either emit therefore needs `br.tse_people` and every year of both pipelines parsed first.

`br.tse_results` mints one person per race, because its results files name a candidate by ballot number within the race. `br.tse_people` merges those persons with the ones `br.municipais`, `br.tse_history`, and `br.tse` hold. `ea parse br.tse_people` reads the electoral court's candidate rosters for every election from 1994 to 2026 from `br.tse_results`' raw files. It writes each candidacy's voter title, tax number, name, and birth date to `titles.parquet`, and the `br.tse_results` candidacy that each roster row becomes to `results.parquet`. The emit places every candidacy of the four pipelines in an exact-key identity, as `br.identity` does, and merges the persons of each identity into the one with the best record: a `br.tse` person first, then `br.tse_history`, then `br.municipais`, and a `br.tse_results` person last. A person whose candidacies fall into two identities is left alone. Each emit merges at most 200,000 records, so the backlog publishes over several runs.

`cz.match` merges Czech municipal candidates, whom `cz.volby` records once per candidacy. Two candidacies join when they carry the same full name in the same council, at elections at most 12 years apart, and the ages the rosters state put their births within a year of each other. A name that two candidates of one council carry in one election joins nothing there, and a group whose births span more than a year, or whose persons hold two Wikidata items, stays apart. By the same-day namesake estimate of ops#4178, name alone would join different people 4.0% of the time in Czech councils, and the age check brings that to 0.07%. Each emit merges at most 200,000 records and writes `merges.tsv.gz` into the changeset folder.

Names are handled in the same way. A pipeline stages a preferred name only when it is the best name it has for that entity and language. A name that should not appear on its entity is removed with `name_drop`, and a caveat that no longer applies is removed with `note_drop`. These rows have IDs, so a re-emit alone cannot delete them.

### Places

A place resolves by its scheme and code, with a date when the scheme reuses codes. Precinct units resolve through `ea.precinct_code`, which builds the same code from the same state, county, and precinct, so two sources for one precinct and year share one unit. Town and municipal areas match to boundary shapes by name within their county. A place's own contest on election day sets its universe, and other sources only fill in what that contest does not hold. Shared display names are settled by a curated list, `identity_names.tsv`, which names places that share a name within a state by their legal type or county.

## Digitization

Scanned compendia, such as nineteenth-century returns, national statistical books, and printed county tables, need their numbers read from page images. Every digitized number stores its source page and a bounding box in `value_locator`. A reviewer can therefore check any number against the printed page.

Two independent passes read each page, either a multimodal model and OCR, or two different models. The passes are reconciled cell by cell and then checked against the totals printed in the source. A disagreement goes to review, with the page crop attached.

PDFs with a text layer need no OCR. `pdftotext -bbox` gives each word with its box, and columns come from clustering the right edges of the words, because blank cells break the token order.

For ruled tables in scans, the OCR pass is `pipelines/ea/scan.py`. It renders each page at 300 dpi, detects the grid from long dark pixel runs, OCRs each cell on its own with Tesseract, and reconciles the results against the printed row and column sums. Full-page OCR fails on the same tables, because it cannot see the cell boundaries.

The batch vision pipeline, `ea scans`, reads scanned county tables with a Claude model through the Message Batches API. Each volume has a manifest in `pipelines/scans/{name}.json`. The manifest lists the source file, the pages, and for each page the crop, the number of bands, the orientation, and one entry per printed column with its contest key and its printed candidate label. `ea scans layout` can write a manifest from the model's own reading of a volume's pages, and `ea scans prepare` fills in the official totals the archive already holds for each column.

The steps run in order, and each step is a single call that advances the batch once:

- `ea scans prepare <name>` renders the crops, fills the official totals, and prints the number of requests.
- `ea scans run <name>` advances the reading. It reads the first pass, checks the tables, sends a second read for pages that fail, and writes `tables.parquet`, `review.json`, and `report.md`.
- `ea scans status` lists every manifest and its open jobs.
- `ea scans emit <name>` writes the tables that passed through the normal changeset path. A comma-separated list of volumes in one folder (`mn-man/1964,1966`) goes into a single changeset.

A column passes when its county rows sum to its printed total, or, if no total is printed, to the official total within the greater of 50 votes or one percent. A page passes when every column passes. A page that still fails after the second read goes to `review.json`, and nothing on that list is published. A person settles it by writing the corrected cells and a note into `overrides.json` in the same folder.

Responses are cached in the raw cache, keyed by the model, the prompt version, the effort level, and a hash of the image. Rerunning a volume with the same inputs costs nothing. Set `EA_SCANS_CACHED` to make every step read only what the cache holds and send no requests. Set `EA_SCANS_RESTAGE` to restage the sets a volume has already published. Batch requests go through `pipelines/ea/batch.py`, which stops before it sends anything when the environment it runs in is not supported. A contributor without that setup can still run any step that reads from the cache.

## Live ingestion

Live workers poll official machine-readable feeds where they exist, and official results pages, such as HTML, PDF, or results platforms that vendors host for election offices, where they do not. They poll at a polite interval, send conditional requests, back off when a server pushes back, and identify themselves with a User-Agent header. Each update writes a live result set and publishes a snapshot with a manifest. Live values never become certified values. Certified results come from post-count imports, which replace the live set through the usual changeset path. Any restore or copy into `live.fetch`, `live.frame`, or `live.issue` must re-run the setval statements in the `live_sequences` migration, or the next insert hits a duplicate key. The architecture document covers how live results are served.

Where a feed splits its counts by ballot type, as Clarity's `VoteType` and Enhanced Voting's `groupName` do, `live.value` keeps one row per channel, using the core channel codes (1 election day, 2 early, 3 postal, 5 provisional). A unit in a frame has either a single row on channel 0 or the full split, never both. The label map in `enr_2026.CHANNELS` turns host labels into channels; a label missing from the map puts that unit on channel 0, and an issue is filed for the feed. Readers that want one total per unit sum the rows across channels. `ea live backfill [--feed id]` rebuilds stored frames by ballot type from their cached raw files, and leaves any frame whose rebuilt totals differ from what it holds.

`live.election` passes the split on as one count per unit, update, and channel, and gives each county baseline the channel mix of the most recent certified result from the same state within the last five years, split by channel: the same office if it was contested, otherwise the president, Senate, or governor race. Each channel's share is its part of the county's votes, and its shift is its share for each option minus the county's share for that option. The live model fits a county with both as two streams: early and postal votes pooled into one, and election-day and provisional votes into the other, each with the share-weighted mix of its channels. Kept apart, the early and postal streams count a voter who moves between the two from one election to the next as a swing: in Georgia, early in-person votes ran 6 points more Democratic than the county in the 2022 Senate race and 1 point less in the 2024 presidential race. `countsAt()` in `src/lib/live/standing.ts` sums the channels back into one count per unit for the map and tables.

`live.ballots` holds administrative counts of ballots in progress for each county: ballots requested, issued, returned, accepted, rejected, remaining, tabulated, and unreturned, as of a time the source states. Each row carries the fetch that read it, the election, the county unit, the stage, a channel (the core codes above, or 0 when the source gives no split), and the count. One fetch can hold many `as_of` times, because a per-voter file such as North Carolina's absentee file rebuilds a whole returned-by-day series. Readers take the latest `as_of` for each county, stage, and channel. These counts are never results and never become certified values; final ballots cast by channel come from post-count imports into the core tables.

Three stages compare ballots with the count, and they mean different things. `remaining` is the number of ballots a county reports as received but not yet tabulated, as of the report time; these rows feed `LiveRace.remaining`. `tabulated` is the number of ballots the same report says the county has already counted. It is stored with the same `as_of` as the matching `remaining` row, so the two can be paired; Arizona's ballot processing reports give it as "Ballots Already Tabulated." `unreturned` is the number of mail ballots sent to voters that have not come back, such as Pennsylvania's "Ballots not returned." Many of those ballots will never be cast, so the live model never reads them as ballots left to count.

The live model in `packages/analytics/src/live.ts` takes two optional inputs built from these counts. `LiveBaseline.floor` is the number of ballots a county had accepted before election day, counting returned mail and early in-person ballots. The model assumes that county will not finish below its floor, and it does not treat a county as done while its count is still under 98% of the floor. `LiveRace.remaining` lists, for each county, the ballots the county reported as left to count at a stated time, plus the count it had tabulated at that time when the source gives one. When the source gives no tabulated count, the model uses the county's latest live count from no more than three hours before the report. The model then assumes the county will finish near that count plus the remaining ballots, and those ballots replace the late-ballot tail for that county.

`live.election` passes both inputs for presidential and statewide races (Senate, governor, lieutenant governor, attorney general, and secretary of state), where every county lies wholly inside the race. A county's floor sums its latest early in-person (channel 2) and mail (channel 3) counts stamped before midnight on election day in the state's time zone, taking `accepted` over `returned` where a source gives both. Remaining counts come only from feeds whose params include `"remaining": true`, the long-count sources whose reports after polls close give the ballots still to count, such as Arizona's ballot processing reports (`us.ballots.az`). When the same feed has a `tabulated` row for the county at the same `as_of`, that count becomes the entry's `counted`; otherwise the model falls back to the county's live count. Pennsylvania's `remaining` rows count mail ballots that voters never returned, so its feed does not set the flag. Rows stamped before the state's poll closing time are dropped. The query runs on each recompute of the night, and the cache key for `live.election` and `live.counties` includes the newest `live.ballots` fetch for the races' elections, so a new row reaches the page on the next request even without a new frame.

The `us.ballots` adapter fills `live.ballots`. Its Florida feed, `us.ballots.fl`, reads the Division of Elections' daily statewide files (`Stats_<election>_VbmVoted.txt`, `Stats_<election>_VbmProvided.txt`, and `Stats_<election>_EarlyVoted.txt`, linked from the statistics page). For each county it writes mail ballots returned (channel 3) and early in-person votes (channel 2) as stage `returned`, and mail ballots sent to voters but not yet returned ("Vote-by-Mail Provided (Not Yet Returned)") as stage `unreturned` on channel 3, each stamped with the county's compile time in Eastern time. The adapter stores the unreturned count as printed and does not add it to the returned count to make an `issued` figure. The first poll also loads the archived history from the `us.ballots` raw cache, with all three counts: every Wayback capture of the statistics page from the 2020, 2022, 2024, and 2026 seasons, plus the final statewide report PDFs for the 2014, 2016, 2018, 2020, 2022, and 2024 generals and the 2014, 2016, and 2018 primaries. In every PDF the county unreturned counts add up to the state total. Archived reports that a poll loaded before the unreturned stage existed are read once more for their unreturned counts only, under their original fetch. The statistics page has no Wayback captures before October 2020, so the earlier seasons come only from the PDFs, which the Division's site blocks to scripts; the cache holds Wayback copies. Run `ea raw pull us.ballots` on the polling host first, or that history is skipped. Rows for special elections are dropped, because they cover only part of a county. The 2026 general also has a daily early-voting series from the Division's per-voter early voting activity file (`EVL_<election>.zip`, linked from the public reports page while the Division posts it). `ballots.early(client, number)` downloads the zip into memory, counts each voter once by county and vote date, and stores only those totals in the raw cache under the archive URL with `#county-day` appended. No voter rows are written to disk. The first poll turns that table into cumulative early in-person counts (channel 2) per county, each stamped 23:59:59 Eastern on the vote date. For 2026, the last day's totals match the statistics page in all 67 counties (3,467,306 early votes).

The North Carolina feed, `us.ballots.nc`, counts accepted and returned ballots from the State Board's per-voter absentee files. Accepted mail ballots track the certified "absentee by mail" votes in `us.nc_channels` within about 5 percent in every county except Onslow in 2024 and Currituck in 2022. Neither gap comes from a coding difference between the two files. The certified results have only four mode columns (election day, early voting or one stop, absentee by mail, and provisional), and the absentee file has only two request types (MAIL and ONE-STOP or EARLY VOTING), so no separate UOCAVA or federal write-in channel exists in either. Onslow 2024 has 4,596 accepted mail ballots (4,602 in the aggregate file, which includes 6 cured ballots) against 3,595 presidential votes in the mail column. The county's early voting matches (58,834 accepted, 58,709 votes), and its provisional column is 1.8 percent of votes, against a statewide median of 0.4 percent, which is about 1,100 votes more than the median rate would give. The likely cause is that Onslow's certified file puts roughly 1,000 mail ballots in the provisional column, but the files do not prove it. Currituck reports more certified mail votes than accepted ballots in both years (320 against 238 in 2022, 728 against 602 in 2024), and Avery does the same in 2024 (413 against 317). Currituck's 2022 mail votes sit in a single precinct named ABSENTEE. The absentee file was loaded once, so ballots cured or accepted after that load would be missing from it, which is a possible cause of these excesses that we have not confirmed. Use the NC accepted counts as a floor for the live model. Do not use them to check certified channel totals.

## Adding a source

Follow these steps to add a source. The example uses a hypothetical source, `xx.example`, on the package path. The `cz.volby` module shows each step in full.

1. **Check the archive first.** Search the existing modules in `pipelines/ea/sources/{iso}/` and `docs/data-model.md`, so that you do not duplicate a publisher or a naming scheme. Note the source's license or its absence. The `licenses` correction pipeline records licenses for sources that publish none.

2. **Make sure the country exists.** A package references its country by `uuid5(NAMESPACE, "polity\x1f{ISO}")` and lists that id in `p.external`. If the archive has no record for the country, add it to `pipelines/ea/sources/world/countries.py` with its Wikidata item and native names, and apply that changeset first.

3. **Create the module.** Add `pipelines/ea/sources/xx/example.py` and define `SOURCE = "xx.example"`.

4. **Write `fetch()`.** Call `raw.fetch(SOURCE, url, suffix=".csv")` for each file the source publishes. Use the source's stable URLs. If the source needs a POST, pass `body=`. If the source is a crawl you ran yourself, store it with `raw.store`.

5. **Write `parse()`.** Read each cached file with `raw.cached(SOURCE, url)` and build the packages: a `geo` package for the places and their shapes, a `registry` package for the parties, bodies, offices, and electoral systems, and one package for each election that depends on both. Make every id with `p.id(kind, *parts)` from the source's own codes, cite each cached file with `p.artifact`, and end each package with `p.write()`. Compare the parsed rows with the totals the source prints, and raise an error on any mismatch. Corrections to the source's own cells are curated constants in the module, each proven by the printed totals and disclosed in a `note` on the result set. `emit()` loads the packages.

   A sketch, where `COUNTRY`, `DAYS`, `packages()`, `results_url()`, `geo()`, and `registry()` come from the module:

```python
def parse() -> None:
    geo().write()
    registry().write()
    for day in DAYS:
        election(day).write()


def election(day: str) -> Package:
    p = Package(
        f"{SOURCE}/{day}",
        SOURCE,
        f"The {day} general election by polling station",
        depends=[f"{SOURCE}/geo", f"{SOURCE}/registry"],
    )
    p.external.add(COUNTRY)
    p.artifact(raw.cached(SOURCE, results_url(day)), p.id("source", "results"))
    ...
    return p


def emit() -> None:
    package.run("load", packages())
```

6. **Check the packages.** Run `uv run ea fetch xx.example` and `uv run ea parse xx.example`. Then run `uv run ea package check` on every key until each one is clean, or until each remaining finding is accepted with `p.accept(code, reason)` and a specific reason. Compare each election's national totals with the totals the authority publishes.

7. **Load them.** Run `uv run ea package ready` on every key, then `uv run ea emit xx.example`. Load the `geo` and `registry` packages with the elections or before them.

8. **Record the source and its citations.** Every fact must trace to a source. Cite each cached file through `p.artifact`. If the source publishes a Wikipedia page, fetch the page with its revision pinned.

9. **Check the cache.** Run `uv run ea raw verify xx.example` to confirm that every indexed file matches its hash, and `uv run ea raw license xx.example` to stamp the license on each entry.

Keep each pipeline small. A source that needs entity matching, such as a people or party matcher, belongs in its own module on the changeset path, which runs after the source loads.
